# CLI & Data Pipeline

## Overview

`tu` is a Node.js CLI tool (binary name: `tu`) that tracks AI coding assistant costs across Claude Code, Codex, OpenCode, Gemini, Copilot, and Kimi. It parses positional arguments into a `{source, period, display}` grammar and dispatches to data-fetching and formatting pipelines.

Entry point: `src/node/core/cli.ts`. Data types: `src/node/core/types.ts`. Data fetching: `src/node/core/fetcher.ts`. Config: `src/node/core/config.ts`.

## Requirements

- The CLI MUST support positional argument grammar: `tu [source] [period] [display]`
- Sources MUST include: `cc` (Claude Code), `codex`/`co` (Codex), `oc` (OpenCode), `gemini`/`gem` (Gemini), `copilot`/`cop` (Copilot), `kimi`/`ki` (Kimi), `all` (default) (`gemini`/`copilot` added 260703-gmcp; `kimi` added 260810)
- Periods MUST include: `d`/`daily` (default), `w`/`weekly`, `m`/`monthly`; combined shorthands `dh`, `wh`, `mh`. `parseDataArgs` recognizes `w`/`weekly` (internal `period` value `"weekly"`) and `wh` (period `"weekly"`, display `"history"`); the `-w`/`--watch` flag is unaffected because `parseGlobalFlags` strips dash-prefixed flags before `parseDataArgs` sees positionals (260703-wkly)
- Display MUST include: bare (snapshot, default), `h`/`history`
- Global flags (parsed by `parseGlobalFlags` into `GlobalFlags`): `--json`/`-j`, `--csv`, `--md`, `--since`/`-s <date>`, `--until <date>` (long-only — `-u` is `--user`), `--full` (long-only boolean — disables the implicit 3-month history cap, see below), `--sync`, `--dry-run` (long-only boolean — parsed globally but honored ONLY by `tu sync`, see below), `--fresh`/`-f`, `--watch`/`-w`, `--interval`/`-i <s>`, `--user`/`-u <user>` (`all` aggregates every user, see below), `--metric <cost|tokens>` (long-only, value-taking — history bar scale, see below), `--by-machine`, `--no-color`, `--no-rain`, `--version`/`-V`/`-v`. Separately, `--skip-brew-update` is an `update`-scoped command-specific flag detected via raw-argv membership — it is NOT in `GlobalFlags`
- `--by-machine` MUST show per-machine cost breakdown columns in tables; works with snapshot and single-tool history; incompatible with all-tools history pivot (warn on stderr and ignore); compatible with `--watch`, `--json`, and `-u`; in single mode, shows one machine (hostname); uses `fetchToolMergedWithMachines` which returns `{ entries, machineMap }` where machineMap is `Map<string, UsageEntry[]>` (machine → entries)
- `--user`/`-u` MUST set a target user for data display (multi mode only); in single mode, warn on stderr and ignore; when targeting a different user, display only metrics repo data (no local ccusage data); when targeting the same user as `config.user`, behave identically to the default (no `-u`) path — perform a local fetch (using cache unless `--fresh`/`-f` is provided), write to the metrics repo, then merge with other machines
- `-u all` (the `ALL_USERS` constant) MUST aggregate every user profile in the metrics repo, repo-only: `fetchToolMerged` flattens `readRemoteEntries(metricsDir, u, null, toolKey)` over `listUsers(metricsDir)` (`src/node/sync/sync.ts`), sums per label with `mergeEntries` (no `maxMergeEntries`, no `fetchHistory`, no `writeMetrics`), then applies `filterEntriesByRange` and `aggregateForPeriod` exactly as the `-u <other-user>` branch does. `fetchToolMergedWithMachines` builds the breakdown map **keyed by user name** instead of machine and hands it to the shared `aggregateMachineMap` helper, so `--by-machine -u all` renders one column per user (legend `Users:` via `FormatOptions.machineLegend`; the JSON `machines` key carries user names). In single mode `-u all` hits the existing `-u` warn-and-clear guard. Because the read is repo-only, today's numbers lag until `--sync` (svlv)
- `all` MUST be rejected as a configured profile name: `assertUserNotReserved(config)` (over the exported pure `isUserReserved(user)`) runs right after `readConfig()` in `main()` (all data commands) and in `runSync()` (`tu sync`, the other day-file writer), printing `Error: config user "all" is reserved (used by -u all)` to stderr and exiting `2` (usage error) (svlv)
- `aggregateMachineMap(machineMap, period, since, until)` (`src/node/core/cli.ts`) MUST be the single tail shared by all three `fetchToolMergedWithMachines` branches (own user, `-u <other-user>`, `-u all`): window each key's entries via `filterMachineMap`, flatten and `mergeEntries`, and aggregate both the flattened series and each key's entries to the requested period, returning `{ entries, machineMap }` (svlv)
- `maxMergeEntries(a: UsageEntry[], b: UsageEntry[])` (exported from `src/node/core/fetcher.ts`, alongside `mergeEntries`) MUST pick, per date label, whichever whole entry has the greater `totalCost` — no field mixing, no summing; on equal `totalCost` the entry from `a` wins (call sites pass the live local fetch as `a`); output MUST be sorted ascending by label and inputs MUST NOT be mutated (pure function, Constitution V)
- In multi mode, the own-user merge pipeline (`fetchToolMerged` and `fetchToolMergedWithMachines` in `src/node/core/cli.ts`) MUST run: live local fetch → `writeMetrics` (never-shrink guarded — see `sync/multi-machine.md`) → `readRemoteEntriesByMachine(metricsDir, config.user, null, toolKey)` (all machines, one walk) → split the own machine out of the map → `effectiveLocal = maxMergeEntries(local, ownSnapshots)` → `mergeEntries(effectiveLocal, otherMachines)`. `fetchToolMergedWithMachines` MUST set the own-machine `machineMap` entry to the max-merged view so `--by-machine` shows the corrected own-machine column and the flattened entries reflect it. Single mode (live entries only, no repo reads) and the `-u <other-user>` path (repo-only, `excludeMachine = null`) are unaffected
- `--json`, `--csv`, and `--md` MUST be mutually exclusive with each other; `--watch` MUST be incompatible with any of them. Violations print `Error: {flag-a} and {flag-b} are incompatible` to stderr and exit `2` (usage error — was `1` before 260717-8h6g; see the Exit-Code Convention requirement below) (`parseGlobalFlags` in `src/node/core/cli.ts`)
- `-j` MUST be an alias of `--json`: it participates in `--json` detection (`rawArgs.includes("--json") || rawArgs.includes("-j")`), is added to the filtered-args skip list, and resolves to `outputFormat: "json"` / `jsonFlag: true`. It joins the format-incompatibility matrix above through `jsonFlag`; error messages keep the canonical `--json` wording, unchanged (260703-sntl)
- `--since`/`-s <date>` and `--until <date>` MUST define a client-side date window for **history display**, parsed by `parseGlobalFlags` as space-separated value-taking flags (same loop as `--interval`/`--user`) and exposed on `GlobalFlags` as `sinceFlag`/`untilFlag`. `--until` is long-only (`-u` is `--user`). Accepted shapes are `YYYY-MM-DD` or `YYYYMMDD` (consistent dashes), normalized to ISO `YYYY-MM-DD` by `normalizeDateFlag`. Validation is **shape-only** — no calendar check, so a well-shaped impossible date (`2026-13-01`) parses and simply yields an empty window. A missing/malformed value prints `Error: --since requires a date (YYYY-MM-DD or YYYYMMDD)` (or `--until` with its own name), and an inverted window (`since > until`) prints `Error: --since must be on or before --until`; each writes to stderr and exits `2` (usage error — was `1` before 260717-8h6g; see the Exit-Code Convention requirement below) (260703-sntl)
- The date window MUST be applied by the pure `filterEntriesByRange` (see `src/node/core/fetcher.ts`) to daily entries **after merge, before `aggregateMonthly`** on every history path, so monthly rollups reflect the window (a partial month sums only in-window days). Coverage: multi mode (`fetchToolMerged`/`fetchToolMergedWithMachines`, including the `-u <other-user>` repo-only branch), single mode (`dispatchAllHistory`/`dispatchSingleTool`), the `--by-machine` per-machine `machineMap` (windowed consistently with the flattened entries via the `filterMachineMap` helper), and the watch-mode `*Lines` variants (filtered each poll via the shared threaded path). All output formats (`table`/`--json`/`--csv`/`--md`) see filtered data. The 60s fetch cache is untouched — `fetchHistory` still fetches/caches the full daily set with `extraArgs === []`; filtering happens after (260703-sntl)
- `--metric <m>` MUST be parsed by `parseGlobalFlags` as a long-only value-taking flag (same loop shape as `--since`) into `GlobalFlags.metricFlag: BarMetric` (`"cost"` default, `"tokens"` opt-in); a missing or invalid value prints `Error: --metric requires 'tokens' or 'cost'` to stderr and exits `2`. In `main()` a non-default metric on a **snapshot** display warns once (`Warning: --metric applies to history display — ignoring.`) and is cleared — same top-level spot as the since/until guard, so watch snapshot warns once at startup. For history displays the metric rides the shared `withCap` FormatOptions merge (alongside `capActive` and the `-u all --by-machine` `machineLegend: "Users"` stamp) into both the one-shot dispatchers and the watch-mode `*Lines` variants; the merge stamps nothing when every field is at its default, so existing output is byte-identical. JSON/CSV/MD emitters have no bars and ignore the flag silently (svlv)
- `--since`/`--until` on a **snapshot** display (bare, no `h`/`history`) MUST warn once on stderr (`Warning: --since/--until apply to history display — ignoring.`) and clear the flags in `main()` before dispatch, mirroring the existing `-u`-single-mode and `--by-machine`-all-tools-history warn-and-clear guards. Because the warn-and-clear runs in `main()` (not inside dispatch), watch snapshot mode warns **once at startup**, not per poll (260703-sntl)
- Daily and weekly history MUST default to an **implicit 3-month window** when no explicit window and no `--full` is given. In `main()`, immediately after the since/until snapshot warn-and-clear guard, when ALL of `display === "history"`, `period !== "monthly"`, `sinceFlag === undefined`, `untilFlag === undefined`, and `!fullFlag` hold, `sinceFlag` is defaulted to `threeMonthFloor()` and a local `capActive` marker is set true. This reuses the shipped `--since` machinery (`filterEntriesByRange`, 260703-sntl) with **zero new filtering logic** — the defaulted floor flows through the same dispatch plumbing as an explicit `--since`, so the fetch cache, multi-mode merge, and every output format (`table`/`--json`/`--csv`/`--md`) and watch mode inherit the cap uniformly through the single defaulted flag. `threeMonthFloor(now = new Date())` (exported from `src/node/core/cli.ts`) returns the first day of the local month two calendar months back as an ISO `YYYY-MM-01` string — a window covering 3 calendar months INCLUDING the current month (2026-07-17 → `2026-05-01`); it uses local date methods (usage labels are local-day based) and `new Date(y, m-2, 1)` normalizes month underflow, so year rollover is handled (2026-01-15 → `2025-11-01`). Weekly aggregation inherits the exact explicit-`--since` semantics: daily entries are filtered before `aggregateWeekly`, so the week containing the floor may surface as a partial leading week labeled with its Sunday (no week-boundary snapping) (260717-yuuj)
- **Monthly history (`mh`) is exempt** from the cap (`period === "monthly"` fails the injection guard, so `sinceFlag` stays `undefined` and `capActive` false — full monthly history is always shown); **snapshot displays are never capped** (`display !== "history"`). Monthly is the compact long-term view — one row per month — and capping it to 3 rows would gut its purpose (260717-yuuj)
- An explicit `--since` OR `--until` MUST disable the implicit cap **entirely** (no intersection with the implicit floor). This falls out of the injection guard's `sinceFlag === undefined && untilFlag === undefined` condition: if the user set either bound, the floor is not applied and `capActive` stays false, so the user's own window is honored. Rationale: intersecting a past `--until` with the implicit floor would silently return an empty window (260717-yuuj)
- `--full` (long-only boolean, no short alias) MUST disable the cap. `parseGlobalFlags` detects it via `rawArgs.includes("--full")`, exposes it as `fullFlag: boolean` on `GlobalFlags`, and strips it in the same boolean-flag pass as the other boolean flags (`--json`/`-j`, `--csv`, `--md`, `--sync`, `--fresh`/`-f`, `--watch`/`-w`, `--no-color`, `--no-rain`, `--by-machine`, `--skip-brew-update`). Behavior: `tu h --full` → full uncapped daily history, no heading hint; `tu mh --full` → silent vacuous no-op (monthly is never capped, so full history is already shown — no warning, since the flag's request is satisfied, not ignored); `--full` on a **snapshot** display (`fullFlag && display !== "history"`) → warns once on stderr (`Warning: --full applies to daily/weekly history — ignoring.`) before dispatch, so watch snapshot mode warns once at startup, mirroring the since/until guard; `--full` combined with an explicit `--since`/`--until` → silently accepted (both express "no implicit cap"; the explicit window still applies) (260717-yuuj)
- `--dry-run` (long-only boolean) MUST be parsed globally but honored ONLY by `tu sync` — it previews a sync without mutating (260717-xuhk). `parseGlobalFlags` detects it via `rawArgs.includes("--dry-run")`, exposes it as `dryRunFlag: boolean` on `GlobalFlags`, and strips it in the same boolean-flag pass as `--sync`/`--fresh`/`--full`/etc. `main()` MUST enforce the fail-fast misuse contract: when `dryRunFlag` is set and `filteredArgs[0] !== "sync"` (covering `tu cc --dry-run`, `tu cc --sync --dry-run`, and bare `tu --dry-run`), it MUST print `Error: --dry-run is supported only with 'tu sync' — run 'tu sync --dry-run' to preview a sync.` to stderr and exit `2` (`EXIT_USAGE` — a usage error; exit 1 in the original 260717-xuhk change, flipped when 260717-8h6g landed the toolkit `0/1/2` convention; asserted by `cli-dry-run-flag.test.ts`), BEFORE any data fetch/dispatch. For `tu sync`, `main()` passes `dryRunFlag` into `runSync(resolveConfigPaths(), TU_HOME, DEFAULT_CONFIG_PATH, dryRunFlag)`. The flag MUST NOT be silently ignored on any invocation — a user who passed `--dry-run` must never get a surprise mutation (see Design Decisions)
- `runSync(configPath?, tuHome?, defaultsPath?, dryRun = false)` (`src/node/core/cli.ts`) MUST, in dry-run mode, run the existing config/mode + metrics-dir guards UNCHANGED (multi-mode required, metrics-dir guard) — so a dry-run in single mode fails exactly like a live `tu sync` — then call `fullSync(guardedConfig, tuHome, true)`, format the returned `DrySyncReport` via `formatDrySyncReport` (would-write with `new`/`update: X → Y` annotations, would-skip with the never-shrink reason, the would-commit message + would-`pull --rebase`/`push`, and a closing `Dry run — nothing written, committed, or pushed.` line), print it to STDOUT, and return exit 0. In dry-run mode `syncMetrics` and the `Synced to ...` success message MUST NOT run. Stdout-not-stderr and exit 0 follow toolkit principle №2 (with `--dry-run` the preview IS the data the caller asked for)
- `--interval` range: 5-3600 seconds, default 10
- **Exit-Code Convention** — the CLI MUST follow the shll toolkit convention (principle №4, *fail fast with actionable errors*): **`0`** success (incl. benign no-ops: `tu update` on a non-Homebrew install / "already up to date"), **`1`** operational failure (well-formed invocation, but the operation could not complete — network/git/Homebrew failure, missing/misconfigured metrics repo, unexpected runtime error; recovery = retry / fix env/config), **`2`** usage error (the invocation itself was wrong — unknown argument/tool/shell, bad flag value, incompatible format flags, `--dry-run` off `tu sync`; recovery = fix the command line). Usage-error sites reference a single named constant `const EXIT_USAGE = 2` in `src/node/core/cli.ts` (no bare `process.exit(2)` literal — code-quality no-magic-numbers). Site classification (verified against live cli.ts): **19 usage-error sites exit `2`** — `runShellInit` unknown-shell **and missing-arg** (the missing-arg branch moved from exit 0 to `EXIT_USAGE` in 260719-ba5w — toolkit `shell-init` standard, see the `tu shell-init` requirement above); the 13 `parseGlobalFlags` branches (`--interval` numeric/min/max, the 6-row `--json`/`--csv`/`--md`/`--watch` incompatibility matrix, `-u requires a username`, `--since`/`--until` date/inverted-window); the `main()` `--dry-run`-misuse guard (`--dry-run` without `tu sync`, added by 260717-xuhk at exit 1 and flipped to `EXIT_USAGE` when 260717-8h6g rebased onto it); `dispatchSingleTool` unknown-tool (+ `SHORT_USAGE` stderr line); the `main` `parseDataArgs` catch (unknown argument, + `SHORT_USAGE` stderr line); and the `main()` `init-metrics` extra-positional-arg check (`Error: init-metrics takes at most one argument (repo-url)` + `SHORT_USAGE` stderr line, asserted by `cli-init-metrics.test.ts` — gzrn). **9 operational sites stay `1`** — `runInitMetrics` (metrics_repo unset, dir-not-a-repo), `runUpdate` (`brew update`/`brew info`/`brew upgrade` failures), `runSync` (metrics_repo unset, clone/dir-missing, sync failed), and the `main().catch` catch-all (which also surfaces the unset/empty-`$HOME` `ConfigHomeError` — `tu: $HOME is not set; cannot locate config` — thrown by `resolveConfigPaths()` on config-reading commands, gzrn). `src/node/tui/watch.ts`'s `process.exit(0)` quit path is untouched. Error message text and stderr routing are byte-identical across the 1→2 flip — only the exit code changed. The `dispatchSingleTool` unknown-tool site is a **defensive branch structurally unreachable via the CLI entry** (every `KNOWN_SOURCES` value normalizes to a valid `TOOLS` key, and `all` routes to `dispatchAll*`), so it is code-inspection-verified rather than end-to-end tested. Exit codes are a **machine-observable contract** (agents/scripts branch on them), so the 1→2 move rides a **minor** version bump per the constitution's Output Stability rule (`just release minor`, 0.9.x → 0.10.0 — the change itself edits no `package.json`). The per-subcommand exit-code table is documented in the CLI-surface spec `docs/specs/usage.md` `## Exit Codes`; subprocess-based tests (`src/node/core/__tests__/cli-exit-codes.test.ts`, which spawns the real CLI via tsx, and the misuse cases in `cli-dry-run-flag.test.ts`) assert exit `2` for the reachable usage-error paths (260717-8h6g)
- Non-data commands (`init-conf`, `init-metrics`, `sync`, `status`, `update`, `shell-init`, `help-dump`, `skill`, `help`) MUST be dispatched before grammar parsing (the dispatch block is in `main()`, `src/node/core/cli.ts`, before `parseDataArgs`). `tu init-metrics [repo-url]` takes at most one positional argument: with a URL it writes `metrics_repo = <url>` into `~/.config/tu/tu.conf` as the CLI-flag layer — it beats an exported `TU_METRICS_REPO` for that invocation's clone — before cloning (write/clone details in [multi-machine](/sync/multi-machine.md)); more than one positional argument prints `Error: init-metrics takes at most one argument (repo-url)` + `SHORT_USAGE` to stderr and exits `EXIT_USAGE` (2) (gzrn). `init-conf` and `init-metrics` share the `ensureUserConf` scaffold helper (creates `$HOME/.config/tu/`, seeds the new file from a legacy `~/.tu.conf` when one exists — cascade and seeding rules in [config-system](/configuration/config-system.md)). `FULL_HELP`'s Setup section advertises them as `tu init-conf         Scaffold ~/.config/tu/tu.conf` and `tu init-metrics [url] Clone metrics repo (url also sets metrics_repo)`. Config path resolution is lazy (`resolveConfigPaths()` at dispatch/read time): config-reading commands (data commands, `init-conf`, `init-metrics`, `sync`, `status`) error with `tu: $HOME is not set; cannot locate config` + exit 1 when `$HOME` is unset/empty, while `$HOME`-free commands (`help`, `--version`, `help-dump`, `skill`, `shell-init`, `update`) keep working (gzrn)
- `tu skill` MUST print the agent usage bundle as **raw markdown to stdout, byte-identical to `docs/site/skill.md`**, with **empty stderr and exit 0** — no rendering, pager, or added framing (`runSkill()` in `cli.ts` is `process.stdout.write(SKILL_MD)`; the `if (cmd === "skill")` dispatch row sits after `help-dump` in the non-data block). The bundle is a static agent **usage briefing** (when-to-use, capabilities map, composition patterns, output/exit-code contract, gotchas) — NOT a flag reference or README clone — adopting the toolkit `skill` standard (260717-uch0). `SKILL_MD` resolves in `src/node/core/skill.ts` via the `__SKILL_MD__` typeof-guard: the shipped bundle uses the esbuild `--define` string (no I/O, Constitution III), dev/tsx reads the canonical `docs/site/skill.md`; the build embed + drift guard live in `build/toolchain.md`. The bundle's exit-code section documents the toolkit `0/1/2` convention (`0` success / `1` operational failure / `2` usage error — the split delivered by 260717-8h6g; see the Exit-Code Convention bullet above)
- `tu shell-init <shell>` MUST emit a static bash/zsh/fish completion script to stdout (scripts live in `src/node/core/completions.ts` as `BASH_COMPLETION`/`ZSH_COMPLETION`/`FISH_COMPLETION` string constants); **no argument writes `SHELL_INIT_USAGE` (usage + install examples) to stderr, leaves stdout empty, and exits `EXIT_USAGE` (2)** — stdout may be eval'd by the user's shell (`eval "$(tu shell-init …)"`), so usage text must never reach it (toolkit `shell-init` standard: a missing/unsupported shell arg is a usage error, convention 2, usage on stderr, stdout empty — 260719-ba5w); unknown shell prints `Unknown shell: {shell}. Supported: bash, zsh, fish` to stderr and exits `2` (usage error — was `1` before 260717-8h6g; see the Exit-Code Convention requirement above). Scripts cover the full grammar (sources, periods, display tokens, non-data subcommands, every long/short flag, and the `bash`/`zsh`/`fish` args to `shell-init` itself). Output is intended for `eval` from the user's shell rc (e.g. `eval "$(tu shell-init zsh)"`), matching the hop/rk shell-init pattern
- `tu update --help` (and `tu update -h`) MUST short-circuit to `console.log(FULL_HELP)` + exit 0 **before** `runUpdate` is invoked (no brew command runs, no state mutates). `FULL_HELP` advertises the literal `--skip-brew-update` substring in its Flags section, which `shll update`'s flag-discovery probe (`tu update --help`) depends on — previously `tu update --help` dispatched to `runUpdate` and ran a real update (help was detected only when `--help`/`-h` was the *first* arg), so the probe both mutated state and never saw the flag (toolkit `update` standard, 260719-ba5w). The short-circuit is scoped to the `update` dispatch only — other surfaces' `--help` behavior (e.g. `tu cc --help` → exit 2 unknown-argument, first-arg `--help` → global help) is unchanged
- `tu update` MUST detect Homebrew installation via `_pkgDir.includes("/Cellar/tu/")`, show a helpful message for non-brew installs (exit 0), and run `brew update` → `brew info` → `brew upgrade` for brew installs with specific error messages per failure. The interactive `brew upgrade tu` call (`stdio: "inherit"`) carries `env: { ...process.env, HOMEBREW_NO_ASK: "1" }` — the env var suppresses Homebrew 6's default ask-mode prompt (`Do you want to proceed with the upgrade? [y/n]`, fired from `ask.rb` only when both stdin and stdout are TTYs, which the inherited stdio satisfies), the `process.env` spread preserves the full inherited environment, and older Homebrew versions harmlessly ignore the unrecognized variable (260812-wdjt — rationale in `build/toolchain.md`). The call carries **no `timeout` option** — the toolkit `update` standard's `MUST NOT impose a short hard timeout on brew upgrade` clause (whose cited incident is the exact prior `timeout: 120_000` that killed a stalled `brew upgrade` and corrupted the keg mid-swap); the piped calls keep generous bounds (`brew update --quiet` 600_000, `brew info --json=v2 tu` 60_000), Node's default SIGTERM satisfying graceful termination (260719-ba5w — brew-safety rationale in `build/toolchain.md`)
- `tu update` MUST accept a `--skip-brew-update` boolean flag which, when present, skips ONLY the internal `brew update --quiet` tap-metadata refresh; the `brew info --json=v2 tu` version check, the up-to-date short-circuit (`latest === PKG_VERSION` → "Already up to date" → return), and `brew upgrade tu` are unaffected. Default (flag absent) preserves the original behavior exactly. The flag is detected at the `update` dispatch via `process.argv.includes("--skip-brew-update")` and passed as a boolean into `runUpdate(skipBrewUpdate = false)`; it is intentionally NOT part of `parseGlobalFlags`/`GlobalFlags` — it is a command-specific flag for `update`, which ignores positional args (flag name matches the cross-toolkit contract string exactly)
- Data fetching MUST use the single `ccusage` binary (all six tools share it — v20 consolidated `@ccusage/codex`/`@ccusage/opencode` into `ccusage codex`/`ccusage opencode` subcommands, and ships first-class `gemini`/`copilot` subcommands) via `child_process.execFile` — invoked with the tool's `binary` as the first argument and a single argv array as the second (`[...tool.prefixArgs, period, "--json", ...extraArgs]`); no shell subprocess is forked. On error, warn on stderr (`warning: {toolName} fetch failed (...), showing zero data`) and resolve the wrapper Promise with `""` so downstream parsing yields `EMPTY` totals. `maxBuffer` remains 10MB
- Fetch results MUST be cached in `~/.tu/cache/` with 60-second TTL; `--fresh` bypasses cache
- The `TOOLS` registry maps all six tool keys (`cc`/`codex`/`oc`/`gemini`/`copilot`/`kimi`; `gemini`/`copilot` added 260703-gmcp, `kimi` added 260810) to a **single ccusage binary** with `ToolConfig` objects carrying `name` (display name), `binary` (executable path), `prefixArgs` (string[] prepended before period/flags), `labelKey` (the JSON key carrying an entry's ISO date label — typed `"date"` | `"period"`, but `"date"` for every registry tool today; see the label-key bullet below), and `needsFilter`. The binary path is resolved once: `${BIN}/ccusage/bin/ccusage` in vendor mode (the native Rust binary, exec'd directly — no `node` interpreter), or `${BIN}/ccusage` in dev mode (the npm JS launcher, `node_modules/.bin/ccusage`). All six tools express a per-agent subcommand via `prefixArgs`: `cc → ["claude"]`, `codex → ["codex"]`, `oc → ["opencode"]`, `gemini → ["gemini"]`, `copilot → ["copilot"]`, `kimi → ["kimi"]` — so `runTool` composes e.g. `ccusage claude daily --json` / `ccusage gemini daily --json`. `cc` uses the `claude` subcommand (was bare `[]`, 260703-bxuh) because ccusage v20's bare `ccusage daily` is an all-agents aggregate; using the per-agent subcommand avoids over/double-counting other agents (260703-ccfx — see the label-key bullet for the accompanying `labelKey` split). Registry **insertion order is the column order** in all-tools views: `cc, codex, oc, gemini, copilot, kimi` — new tools always append so existing columns keep their positions (Output Stability — 260703-gmcp). `runTool`'s argv composition is unchanged; `ToolConfig` gained the `labelKey` field (an addition, no removals), so `cli.ts`/`sync.ts` consumers (`Object.keys(TOOLS)`, `TOOLS[k].name`) are unaffected (260703-ccfx)
- `needsFilter` tools (Codex, OpenCode) strip lines starting with `[` before JSON parsing (`stripNoise`). As of v20 (260703-bxuh) ccusage emits clean JSON on stdout, so `stripNoise` is a **defensive no-op** in practice — `needsFilter` is retained for codex/oc pending a later cleanup, not because current output requires it
- Date labels MUST be normalized to ISO (`normalizeLabel`). The JSON key carrying an entry's ISO date label lives per-tool as `ToolConfig.labelKey`, and is **`"date"` for all six per-agent subcommands** (`claude`/`codex`/`opencode`/`gemini`/`copilot`/`kimi`) at ccusage v20 — only the bare all-agents aggregate (`ccusage daily`, which tu never calls) emits `"period"`. The earlier claim that `codex`/`oc` emit `"period"` was a ccfx-era error (guessed, never live-verified); it was corrected here after inspecting the vendored binary and the upstream source at tag v20.0.14 (the shared serializer `agent_summary_json` maps `period_key(Daily) = "date"` for opencode/gemini/copilot; codex has its own identical `Daily => "date"` mapping; the codex snapshot fixture shows `"date"`; `adapter/all/report.rs` is the only serializer emitting `"period"`) (260703-gmcp). The `labelKey` field replaced the earlier period-keyed `LABEL_KEY` const (which mapped both `daily` and `monthly` to `"period"`) — a const cannot distinguish tools that share a period once key spelling diverges by tool; the mechanism is retained because the key varies by serializer, so a future divergence stays a data-only change (260703-ccfx). `fetchHistory` maps entries with `tool.labelKey`; `pickCurrentEntry` takes the label key as a defaulted 4th parameter (`labelKey = "date"` — flipped from `"period"` in 260703-gmcp so the default matches every registry tool and an omitted arg still resolves real labels) supplied by its caller — `fetchTotals` passes `tool.labelKey` (`"date"`) explicitly regardless. Only raw ccusage JSON is affected (all fetches run `period = "daily"`; weekly/monthly are aggregated client-side from the already-normalized `UsageEntry.label`), so `labelKey` applies exactly where raw entries are parsed. `normalizeLabel` passes ISO labels through unchanged for either key spelling (daily `"2026-07-03"`, monthly `"2026-07"`), so no label-format work is needed; the human-readable `"Feb 14, 2026"` → `"2026-02-14"` path remains for defensive robustness (260703-ccfx)
- Weekly and monthly aggregation MUST be computed client-side from daily entries (never via a ccusage `weekly`/`monthly` subcommand invocation — the fetch stays daily-only so aggregation runs post-merge and inherits the fetch cache, multi-mode machine merge, `--user`/`--by-machine` views, and watch mode). `aggregateMonthly` slices the label to `YYYY-MM`; `aggregateWeekly` keys on `weekLabel(e.label)`; both accumulate all numeric fields (`inputTokens`, `outputTokens`, `cacheCreationTokens`, `cacheReadTokens`, `totalTokens`, `totalCost`) into a map, return entries sorted ascending by `label` via `localeCompare`, and are pure (inputs not mutated, Constitution V). `weekLabel(dailyLabel)` maps a daily ISO label to the ISO date of that week's Sunday (`getUTCDay() === 0`) via UTC date arithmetic on the date-only label string — immune to local DST transitions — yielding a plain `YYYY-MM-DD` label (Constitution V) aligned with `ccusage weekly --json`'s default `--start-of-week sunday` output so `tu weekly` rows compare row-for-row with `ccusage weekly`. Aggregation is routed through `aggregateForPeriod(period, entries)` (`src/node/core/fetcher.ts`): `"monthly"` → `aggregateMonthly`, `"weekly"` → `aggregateWeekly`, `"daily"`/other → identity; the dispatch/fetch call sites in `cli.ts` thread this single mapping (single-mode snapshot/history branches guard on `period !== "daily"`) instead of scattered `period === "monthly"` conditionals. The `--since`/`--until` window (`filterEntriesByRange`, 260703-sntl) is applied to daily entries BEFORE `aggregateForPeriod`, so weekly/monthly rollups reflect the filtered window. Weekly/monthly labels are display-only — `writeMetrics` always persists daily entries, so nothing aggregated is baked into the metrics repo (260703-wkly)
- `currentLabel(period, now)` (`src/node/core/fetcher.ts`) MUST return the current period's ISO label in **local time** (matching how daily/monthly already key on the user's local "now") so snapshot dispatch picks the right entry: `"monthly"` → `YYYY-MM`, `"weekly"` → the current week's Sunday (`setDate(getDate() - getDay())`, which normalizes month/year underflow), `"daily"`/default → `YYYY-MM-DD`. `weekLabel` uses UTC arithmetic (timezone-less date-only labels), while `currentLabel`'s weekly case uses local-time date methods — the two are intentionally different because they answer different questions (grouping a fixed label vs. resolving "now") (260703-wkly)
- Output format is represented by `outputFormat: "table" | "json" | "csv" | "md"` on `GlobalFlags` (`src/node/core/cli.ts`). `parseGlobalFlags` resolves the enum from mutually-exclusive flags; dispatch functions (`dispatchAllHistory`, `dispatchAllSnapshot`, `dispatchSingleTool`) fetch once and switch on `outputFormat` to call `emitJson`, `emitCsv`, `emitMarkdown`, or the existing `print*` renderers. Legacy `jsonFlag` boolean is retained for internal compatibility

## Design Decisions

- **Single binary via esbuild**: All TypeScript is bundled into `dist/tu.mjs` with `--platform=node --format=esm`. No runtime transpilation needed.
- **ccusage as data source**: Token/cost data is fetched by shelling out to `ccusage` rather than reading JSONL files directly. The `--json` flag is always passed to get structured output. As of 260703-bxuh (v20 migration) a **single** `ccusage` binary serves every tool; as of 260703-ccfx all tools route through a per-agent subcommand (`claude`/`codex`/`opencode`, joined by `gemini`/`copilot` in 260703-gmcp and `kimi` in 260810), reusing the existing `prefixArgs`/`runTool`/`BIN` machinery rather than adding parallel paths. *Historical (pre-v20):* three separate packages (`ccusage`, `@ccusage/codex`, `@ccusage/opencode`) were shelled out to; the latter two were deprecated upstream (final release 19.0.0) and their functionality moved into `ccusage`'s built-in subcommands.
- **`cc` uses the `claude` subcommand, not bare `ccusage daily`** (260703-ccfx): ccusage v20 redefined bare `ccusage daily` as an **all-agents aggregate** (JSON carries `agent: "all"` + `metadata.agents`; `--all` is a compat no-op), so the v20 migration's `cc → prefixArgs: []` mislabeled the aggregate of *every* locally-detected agent as Claude Code — over-counting `tu cc` and **double-counting** the all-tools total (e.g. codex usage landing under both the `cc` and `codex` columns). *Why latent:* on a claude-only machine the aggregate equals claude, so numbers matched and the bug shipped silently; it corrupts numbers the moment any other agent's transcripts appear locally — and cost accuracy is the tool's whole purpose (Constitution I). *Fix:* map `cc → ["claude"]`, reusing the per-agent subcommand mechanism already used by `codex`/`oc` (a one-line registry change, minimum pathways) — *Rejected:* client-side filtering of the bare aggregate via `metadata.agents` (adds a parsing path for data ccusage already serves cleanly per-agent). The wrinkle motivating the per-tool `labelKey` lookup (`ToolConfig.labelKey`): ccfx believed the `claude` subcommand emitted its date label under `"date"` while `codex`/`opencode` still used `"period"`, so a single const could no longer serve all tools. That belief was half-right — the mechanism is genuinely warranted (the key *can* vary by serializer) but the specific `codex`/`oc → "period"` claim was wrong and never live-verified. Verification at v20.0.14 (260703-gmcp) found **all five per-agent subcommands emit `"date"`**; only the unused bare aggregate emits `"period"`. So the registry is uniformly `"date"` today, and the per-tool mechanism now guards a *potential* future divergence rather than an actual one — see the label-key requirement above.
- **Cache-first fetching**: A filesystem cache (`~/.tu/cache/{toolKey}-daily.json`) avoids re-scanning 500MB+ of JSONL files on every invocation. 60s TTL balances freshness with performance.
- **Positional grammar over subcommands**: `tu cc mh` reads more naturally than `tu history --source cc --period monthly`. Source aliases (`co` -> `codex`) keep it terse.
- **Two dispatch paths**: Non-watch mode calls `dispatchAllHistory`/`dispatchAllSnapshot`/`dispatchSingleTool` which print directly. Watch mode calls `*Lines` variants returning `string[]` for compositor consumption.
- **`execFile` over `exec` for child processes** (260423-lx0g): ccusage invocations in `fetcher.ts` and all git calls in `sync/sync.ts` use `execFile(binary, argv[])` instead of `exec(cmdString)`. Removes the `/bin/sh` fork per call, eliminates shell-injection surface on interpolated values (`config.metricsDir`, `config.user`), and passes paths containing spaces/quotes as literal argv entries. `TOOLS` splits the compound command into `binary` + `prefixArgs` to map directly onto the `execFile` signature.
- **Output format as a single enum plumbed through dispatch** (260423-lx0g): `outputFormat: "table" | "json" | "csv" | "md"` is resolved once in `parseGlobalFlags` and each dispatch function switches on it in one place. Avoids multiplying `if (jsonFlag) ... else ...` branches as new formats are added.
- **Static shell completion scripts** (260423-lx0g): Bash/zsh/fish completion scripts are hardcoded string constants in `src/node/core/completions.ts`. No dynamic lookup (the grammar is stable and runtime `tu --list-*` calls would add 50-200ms per tab-press); no `$SHELL` auto-detection (explicit arg avoids silent mismatches when `$SHELL` and the running shell diverge).
- **`--skip-brew-update` detected via raw-argv membership, not `parseGlobalFlags`** (260531-e96v): The `update` dispatch passes `process.argv.includes("--skip-brew-update")` into `runUpdate` rather than threading the flag through `parseGlobalFlags`/`GlobalFlags`. It is command-specific to `update` (which ignores positional/data args); routing it through the shared data-flag path would broaden the blast radius and risk perturbing unrelated flag handling. Membership testing matches the existing `rawArgs.includes(...)` idiom (e.g. `--sync`). The cross-toolkit contract mandated the exact flag name `--skip-brew-update` (no alias).
- **Client-side weekly aggregation, threaded via `aggregateForPeriod`** (260703-wkly): the weekly period is computed client-side from daily entries (mirroring `aggregateMonthly`), applied post-merge, rather than passing through to a `ccusage weekly` subcommand. *Why*: post-merge aggregation inherits the fetch cache, the multi-mode machine merge (incl. the own-machine max-merge correction), `--user`/`--by-machine` views, and watch mode with zero extra plumbing. *Rejected*: `ccusage weekly` pass-through — it would bypass the multi-mode merge pipeline and skip the daily fetch cache (extra ccusage args bypass caching in `fetchHistory`). The label is the **Sunday-start week-start ISO date** (`YYYY-MM-DD`), chosen to satisfy Constitution V without an amendment and to match `ccusage weekly --json`'s default output row-for-row; a distinct `YYYY-Www` form was rejected as it would require a constitution amendment. Rather than add a third scattered `period === "weekly"` branch at the ~8 monthly-conditional dispatch/fetch sites, a single `aggregateForPeriod(period, entries)` mapping is threaded through them (single-mode snapshot/history branches generalized from `=== "monthly"` to `!== "daily"`) — fewer distinct code paths (minimum pathways), monthly/daily behavior byte-preserved. formatter.ts needed no change (period-generic: headings interpolate `(${period})`, the label column is literally `"Date"`, weekly labels are `YYYY-MM-DD` like daily).
- **Own-machine snapshots max-merged into the live view** (260610-srmi): Claude Code purges transcripts older than ~30 days, so the live ccusage fetch under-reports old days; the previous pipeline excluded the machine's own repo dir from remote reads (`excludeMachine = config.machine`), leaving its own synced history invisible to itself once transcripts were purged. The multi-mode pipeline now reads all machines in one `readRemoteEntriesByMachine(..., null, ...)` walk, splits out the own machine, and applies per-day whole-entry max (`maxMergeEntries`) to the own share before the existing sum-merge with other machines. Max, not sum: a partially-purged day still yields a residual live entry, and summing residual + snapshot would double-count the surviving transcripts. Reuses the existing by-machine walk unchanged (minimum pathways) instead of adding a single-machine read helper; merged totals only ever increase relative to the pre-change pipeline. Watch mode shares the same fetch path and is corrected for free.
- **Client-side date filter over ccusage pass-through** (260703-sntl): `--since`/`--until` filter merged `UsageEntry[]` in `tu` (the pure `filterEntriesByRange`) rather than forwarding the flags to ccusage. Two reasons make pass-through wrong: (i) extra ccusage args bypass the 60s fetch cache — `fetchHistory` caches only vanilla calls (`extraArgs.length === 0`), so a pass-through window would fetch cold every invocation; and (ii) pass-through cannot filter multi-mode remote entries — they are read from the metrics repo (`readRemoteEntries`/`readRemoteEntriesByMachine`), never through ccusage, so a ccusage-side window would silently miss them. Because labels are already normalized ISO strings, lexicographic string compare is a correct total order, making a post-fetch filter both simple and exact. The filter is applied **before `aggregateMonthly`** (not on monthly labels after aggregation) so a boundary month sums only its in-window days rather than its full-month total. *Rejected*: ccusage `--since`/`--until` pass-through (cache bypass + multi-mode blind spot).
- **Implicit 3-month cap as a defaulted `sinceFlag` at the guard seam** (260717-yuuj): the default 3-month window on daily/weekly history is implemented purely client-side by defaulting `sinceFlag = threeMonthFloor()` in `main()` (at the same seam as the since/until snapshot guard) rather than adding any new filtering path — the defaulted floor rides the existing `filterEntriesByRange` machinery (260703-sntl) exactly as an explicit `--since` does. *Why*: one code path, zero new filtering logic, the 60s fetch cache and multi-mode remote merge are untouched, and every output format + watch mode inherit the cap uniformly through the single defaulted flag (minimum pathways, code-quality.md). *Why the cut is "from the 1st of a month"*: the user asked for it, and a month-aligned floor makes the window (and the resulting Total row) a clean N-calendar-month figure. *Why explicit `--since`/`--until` disables it entirely (no intersection)*: intersecting a past `--until` with the implicit floor would silently empty the output — the guard's `sinceFlag === undefined && untilFlag === undefined` condition makes any explicit bound turn the cap off. *Why monthly is exempt*: `mh` is already one compact row per month (the long-term view); a 3-row cap would gut it. *Rejected*: passing `--since` through to ccusage (cache bypass + multi-mode blind spot, same rationale as 260703-sntl). This is a **breaking default-output change** (the default daily/weekly Total becomes a 3-month total instead of all-time), so it carried a minor version bump 0.7.0 → 0.8.0 per the constitution's Output Stability rule.
- **`--dry-run` parsed globally, honored only by `tu sync`, misuse fails fast** (260717-xuhk): the flag is detected in `parseGlobalFlags` (like `--sync`) but only `tu sync` acts on it; any other invocation carrying it errors on stderr and exits with a usage error. This mirrors `--skip-brew-update` (globally observed, one command honors it) but with an explicit error rather than a silent ignore. *Why fail-fast, not preview-then-proceed*: the multi-mode fetch path (`fetchToolMerged`/`fetchToolMergedWithMachines`) writes day-files OUTSIDE the sync boundary on every data command, so a combined `tu cc --sync --dry-run` that "previews then proceeds" would write the very day-files it just previewed via the fetch path — a lying dry-run. Fail-fast is the honest contract, and strict→loose is the non-breaking direction if combined support is ever wanted. *Exit code*: the original change exited 1, deliberately deferring the toolkit's exit-2 usage convention to backlog `[8h6g]`; when 260717-8h6g landed the `0/1/2` split, the misuse guard was flipped to `EXIT_USAGE` (2) — it is a usage error, consistent with every other usage-error site. *Rejected*: silently ignoring the flag (a user who passed `--dry-run` must never get a surprise mutation); honoring it on data commands (would require gating the fetch-path writes too, far beyond scope, and still would not be a pure preview). The preview/no-mutation mechanics themselves live in `sync/multi-machine.md`.
- **Named constant `EXIT_USAGE = 2`, not a `usageError()` helper** (260717-8h6g): the 1→2 flip introduces a single module-level `const EXIT_USAGE = 2` swapped into the existing `process.exit(...)` calls at the usage-error sites (16 in the original change; the `--dry-run` misuse guard from 260717-xuhk joined as the 17th at rebase integration), rather than a `usageError(msg): never` helper. *Why*: the 14 `parseGlobalFlags`/`runShellInit` sites already own their `console.error(msg)` call, and the two `SHORT_USAGE` sites (`dispatchSingleTool`, the `main` `parseDataArgs` catch) print a **second** stderr line before exiting — a one-message helper would not compose with that two-line stderr without extra parameters, and would pull the message text away from each branch (hurting local readability). A plain constant is the minimal, byte-preserving change and satisfies no-magic-numbers. *Rejected*: `usageError()` helper (doesn't compose with the `SHORT_USAGE` two-liner cleanly). Coverage note: the `dispatchSingleTool` unknown-tool site (site 15) is a **defensive branch unreachable via the CLI entry** — every `KNOWN_SOURCES` value normalizes to a valid `TOOLS` key and `all` routes to `dispatchAll*`, so triggering it end-to-end would require a test-only export (Test Integrity forbids that); it is code-inspection-verified rather than exercised by `cli-exit-codes.test.ts`. Because exit codes are a machine-observable contract, the change ships behind a **minor** release (`just release minor`, 0.9.x → 0.10.0) per Output Stability.
