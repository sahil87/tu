# Build & Test Toolchain

## Overview

The shipped `src/node/` tree uses esbuild for bundling and the Node.js built-in test runner (via `tsx`) for testing; the unshipped `src/go/` successor is a plain Go module built, linted, and tested through `just go-*` recipes and its own CI lane. Distributed via Homebrew tap from the sahil87 GitHub org.

## Requirements

- Build MUST use esbuild: `esbuild src/node/core/cli.ts --bundle --platform=node --format=esm --outfile=dist/tu.mjs --banner:js='#!/usr/bin/env node'`
- Tests MUST run via `npx tsx --test 'src/node/**/__tests__/*.test.ts'` (Node.js built-in test runner, not Jest/Vitest)
- Go successor code lives under `src/go/` and MUST NOT ship until cutover; its tests are `_test.go` siblings, never `__tests__/` folders (constitution v1.2.0 § Go Transition). `fab/project/config.yaml` scopes fab to both trees (`source_paths: [src/node/, src/go/]`) and attributes `**/*_test.go` to tests in the true-impact breakdown
- Go module: `src/go/go.mod` declares `module github.com/sahil87/tu`, `go 1.25`, and no dependencies (no `go.sum`). Layout mirrors the sibling Go tools shifted one level: `src/go/cmd/<name>/` entry points (`tu/`, `tudiff/`, `fakeccusage/`, `fakegit/`) and shared code under `src/go/internal/<pkg>/`, whose first package is `internal/harness` (the fixture-corpus machinery — see [differential-harness](/harness/differential-harness.md)) (plan `fab/plans/sahil/26-09-15-go-port.md` D5)
- Go entry point `src/go/cmd/tu/main.go` implements only the toolkit `version` contract: `--version`/`-V`/`-v` (anywhere in args) print exactly `tu version <v>` to stdout and exit 0, where `<v>` is `var version = "dev"` stamped via `-ldflags "-X main.version=…"` and `v`-prefixed when it starts with a digit (`dev` stays `dev`). Every other invocation writes `tu: not implemented (Go port in progress)` to stderr and exits 1 — the placeholder the differential harness (plan row P4) starts from. The logic sits behind a testable `run(args, stdout, stderr) int` / `versionLine(v) string` seam pinned by `src/go/cmd/tu/main_test.go` (260915-h1iv)
- Go recipes (`justfile`): `just go-build` writes `bin/tu` (gitignored) stamped with `-X main.version=v<package.json version>` (read via `node -p`); `just go-test` runs `cd src/go && go test ./... -count=1`; `just go-lint` fails on any `gofmt -l` output under `src/go/` then runs `go vet ./...`. No `golangci-lint`. The Node recipes (`setup`/`test`/`run`/`build`/`release`/`release-notes`) are unchanged (260915-h1iv). `just harness-build` builds the three differential-harness binaries into `bin/harness/` (gitignored via `bin/`) — `tudiff` plus the fakes `ccusage` and `git`, named for the tools they impersonate so `tudiff run` can prepend `bin/harness` to `PATH`; `just harness-capture *ARGS` depends on `harness-build` and runs `bin/harness/tudiff capture {{ARGS}}`. `just go-diff *ARGS` depends on `build go-build harness-build` and runs `bin/harness/tudiff run {{ARGS}}` — the byte-diff of `node dist/tu.mjs` against `bin/tu` over `harness/matrix.json`; exit 1 while any case is red — the count is the port's burndown, not a gate yet (i9hc). `harness/matrix.json` (the case-group argument matrix) and `harness/metrics-repo/` (the seeded metrics-repo mini-clone copied into the harness's multi-mode `$HOME` variants) are committed harness data beside the placeholder corpus (i9hc). `go-test`, `go-lint`, and `go vet ./...` cover the harness packages (`cmd/tudiff`, `cmd/fakeccusage`, `cmd/fakegit`, `internal/harness`) through their existing `./...` sweeps, and fixture-corpus validation (`src/go/internal/harness/corpus_test.go`) runs inside the existing `go-build-and-test` CI lane — no CI workflow change (r7dh)
- TypeScript config: `target: ES2022`, `module: NodeNext`, `strict: true`
- Package MUST be distributed as ESM (`"type": "module"`)
- Binary name MUST be `tu` (via `"bin": { "tu": "dist/tu.mjs" }`)
- `prepublishOnly` MUST run `npm run build`
- Published files: `dist/`, `tu.default.conf`
- Node.js engine requirement: `>= 18`
- Dependencies: `@types/node`, `esbuild`, `tsx`, `typescript`, `ccusage` (single package, `^20.0.14`) — all devDependencies; ccusage is build-time only, vendored into `dist/vendor/` during build. codex/opencode functionality is built into `ccusage` as `ccusage codex`/`ccusage opencode` subcommands (260703-bxuh)
- Vendor distribution: `ccusage@20` ships **no JS implementation** — the main package is a launcher over a per-platform native Rust binary. The build step vendors that single binary into `dist/vendor/ccusage/bin/ccusage` (`chmod 0755`, clean-before-copy via `rm -rf dist/vendor`)
- Platform-package mapping (`scripts/build.sh`): the native binary lives in an `@ccusage/ccusage-{platform}-{arch}` npm package declared as an `optionalDependency` of `ccusage`. `build.sh` derives the host package name via `node -p '`@ccusage/ccusage-${process.platform}-${process.arch}`'` and copies its `bin/ccusage`. npm selects the correct host binary at `npm install` time; because the Homebrew formula builds from source on the user's machine (`npm install --include=dev` + `npm run build`), platform selection is automatic per-install — no per-platform release artifacts and no `release.yml` changes. Supported platforms are exactly Homebrew's: darwin/linux × x64/arm64. win32 is out of the vendor path (Homebrew-only distribution); Windows dev mode still works via the npm launcher
- Fail-loud build guard (`scripts/build.sh`): if the host's `@ccusage/ccusage-{platform}-{arch}/bin/ccusage` is absent, the build prints `error: {pkg} not installed — unsupported platform or npm install skipped optional deps` to stderr and exits 1 (no partial `dist/vendor`). Fail-loud is correct here because this is build-time, not a runtime data source — Constitution II (graceful degradation) governs runtime, not the build
- BIN resolution: Vendor-first — resolves `vendor/` relative to `__dirname` (via `import.meta.url`); falls back to `node_modules/.bin/` when vendor dir absent (dev mode)
- Tool invocation: Vendor mode execs the native binary directly at `${BIN}/ccusage/bin/ccusage` (no `node` interpreter); dev mode uses `${BIN}/ccusage` (the npm JS launcher). See `cli/data-pipeline.md` for the single-binary tool registry and per-tool `prefixArgs`

### Help-dump → shll.ai (build-time CLI help artifact)

- **`help-dump` is an in-binary subcommand** — `tu help-dump` (wired in `cli.ts` → `runHelpDump()`) prints tu's CLI help as the cross-tool contract `{tool, version, schema_version: 1, root: Node}` (where `Node = {name, path, short, usage, text (raw byte-for-byte --help), commands: Node[]}`) to **stdout only**, exit 0, **nothing on stderr** (shll.ai treats any stderr on success as contract drift). The envelope MUST NOT carry `captured_at` — the capture timestamp is owned by shll.ai's puller (a tool cannot know its own capture time), per the toolkit `help-dump` standard (`shll standards help-dump`) (260717-rdo3). tu's document is flat (`commands: []`) because tu prints no per-subcommand help pages. The pure contract assembly lives in `src/node/core/help-dump.ts` (`buildHelpDoc`), bundled into the binary by esbuild and unit-tested directly (the pinning test `src/node/core/__tests__/help-dump.test.ts` asserts `captured_at` is ABSENT).
- This is the surface **shll.ai's pull cron actually invokes** against the brew-installed binary (`<binary> help-dump`, uniform with the 6 Go/Cobra tools). It MUST be a real binary subcommand for that reason — see the gotcha below. `name`/`version`/`description` are embedded at **build time** via esbuild `--define` (`__PKG_NAME__`/`__PKG_VERSION__`/`__PKG_DESCRIPTION__` in `build.sh`), because the Homebrew bottle ships only `dist/` (no `package.json` at runtime). In dev (tsx, defines absent) `cli.ts` falls back to walking up to `package.json` once. The raw help `text` is `FULL_HELP + "\n"`, byte-for-byte identical to `tu --help` (`console.log` appends the newline). This is a build/interop artifact, so it does NOT follow Constitution II graceful degradation — it is deterministic and side-effect-free.
- **`scripts/help-dump.mjs` (run via `npm run help-dump`) is a thin local convenience wrapper** — it runs the built binary `node dist/tu.mjs help-dump`, captures stdout, writes `help/tu.json`, and self-validates. It holds **no contract logic** (no drift risk); the binary is the single source of truth. Still plain `node` (`node:` built-ins only, no tsx — Constitution III).
- `help/tu.json` is a **build-local artifact** — gitignored (`help/`), never committed to the tu repo; `sahil87/shll.ai` is the source of truth. tu does not emit or transport it via CI; the dump is invoked outside tu's CI — locally (`npm run help-dump`), and by shll.ai's pull cron (which runs `tu help-dump` against the brew-installed binary).
- shll.ai **pulls** via its own scheduled cron (`scheduled-help-refresh.yml` in `sahil87/shll.ai`) that `brew install`s tu, runs `tu help-dump`, validates, and **direct-commits** to its own `main` using the default `GITHUB_TOKEN`. The cron is the single trusted writer of `help/tu.json`; tu pushes nothing (260603-dmhw). tu does NOT emit `captured_at`; the puller stamps it after capture, as the standard assigns (260717-rdo3).
- A **`.github/workflows/ci.yml`** runs build + tests (`npm ci`, `npm run build`, `npm test`) on **both** `pull_request: branches: [main]` (to gate merges) **and** `push: branches: [main]` (post-merge / release-merge verification) — single `ubuntu-latest` + node 20 lane, action SHAs pinned identically to `release.yml`. A second job **`go-build-and-test`** (`ubuntu-latest`; `actions/setup-go` pinned `40f1582b…` v5 with `go-version-file: src/go/go.mod` and `cache: false` until a `go.sum` exists; `extractions/setup-just` pinned `dd310ad5…` v2) runs `just go-lint`, `just go-build`, `just go-test` so lint has exactly one definition (260915-h1iv); the same lane's `go-test` carries the harness packages' unit tests and the committed fixture-corpus validation with no workflow change (r7dh). A third job **`go-diff`** (`ubuntu-latest`; same pinned checkout / setup-node 20 / setup-go (`go-version-file: src/go/go.mod`, `cache: false`) / setup-just SHAs, `npm ci`) runs `just go-diff --placeholder` with `continue-on-error: true` on the harness step only — every case is red until Phase 1 lands — and uploads `bin/harness/report/` via `actions/upload-artifact` pinned to the v4 SHA the sibling toolkit repos use (`if: always()`, artifact name `tudiff-report`) (i9hc). The job is informational: it is NOT in `ci-gate`'s `needs`, so it can neither block a merge nor turn the gate red; plan row R3 removes `continue-on-error` and adds the job to `ci-gate`. The aggregating **`ci-gate`** job (`needs: [build-and-test, go-build-and-test]`, `if: always()`, single `ubuntu-latest` lane) succeeds only when both lanes succeeded; `if: always()` makes the gate resolve to a definitive pass/fail (a skipped required check would otherwise block PRs). `ci-gate` is the single stable **required status check** that gates PR merges to `main`, enforced by a branch **ruleset** on `main` (applied via `scripts/ci-gate-ruleset.sh` — an idempotent, dry-run-default helper; running the live mutation is a documented admin action, NOT performed by the pipeline). It does NOT publish anything (GitHub Release, Homebrew tap) — those external side effects live in `release.yml` (its `release` job runs on a `v*` tag push, on `workflow_dispatch`, and on a `release`-labeled merge to `main`).
- **`release.yml`**: on the `v*` tag-push path it builds and publishes (GitHub Release + Homebrew tap update); it carries **no help-dump/shll.ai steps** (260603-dmhw). No workflow uses `SHLLAI_TOKEN`. It carries the release-PR-merge entry point — a `tag-on-release-merge` job (on push to `main`) detects a `release`-labeled merged PR, creates+pushes the `v*` tag, and exposes outputs so the `release` job runs in the SAME workflow run via `needs`/`always()`.

### Skill bundle embed → `__SKILL_MD__` (build-time, drift-guarded)

- The `tu skill` agent usage bundle (canonical source `docs/site/skill.md`, 117 lines, ≤150 hard cap) is **embedded at build time as an esbuild `--define` string constant** — `SKILL_DEF=$(node -p 'JSON.stringify(require("fs").readFileSync("docs/site/skill.md", "utf8"))')` piped into the esbuild invocation as `--define:__SKILL_MD__="$SKILL_DEF"`, immediately alongside the `__PKG_VERSION__`/`__PKG_NAME__`/`__PKG_DESCRIPTION__` defines. This reuses the exact `__PKG_*__` mechanism (not an esbuild text loader — zero new build machinery); `JSON.stringify` yields a correctly-quoted single-word JS string literal, so no extra shell escaping. Resolution + dev fallback live in `src/node/core/skill.ts` (`SKILL_MD` typeof-guard, mirroring `cli.ts`'s `__PKG_*__` guard) — see `cli/data-pipeline.md`. The shipped bundle performs NO runtime file read for the bundle (Constitution III); dev/tsx reads the canonical file.
- **Byte-identity is by construction, not a committed copy**: the define reads `docs/site/skill.md` directly at bundle time, so there is **no committed embedded copy and no sync script**. This diverges from the shll `go:embed` sync mechanism, which needs a file copied *inside* the Go package; esbuild `--define` reads the canonical file directly, satisfying the standard's byte-identical-and-guarded intent without the copy.
- **Post-build drift guard** (`scripts/build.sh`, after the esbuild + vendor steps so a complete build is validated): `node dist/tu.mjs skill | cmp -s - docs/site/skill.md` — on mismatch prints `error: tu skill output drifted from docs/site/skill.md` to stderr and `exit 1`. This is the layer that guards the **shipped artifact** (the tsx unit tests never exercise `dist/tu.mjs`); it is placed after vendoring to run against the same bundle users ship. Fail-loud is correct here — build-time, not a runtime data source (Constitution II governs runtime, not the build), mirroring the vendor fail-loud guard. A co-located tsx test (`src/node/core/__tests__/skill.test.ts`) additionally pins the dev-fallback path: `SKILL_MD` byte-identity vs. the canonical file, ≤150-line budget, static-only sanity, and the CLI `skill` dispatch contract (stdout=bundle, empty stderr, no non-zero exit).

## Design Decisions

- **esbuild over tsc**: Single-file bundle avoids `node_modules` resolution at runtime and produces a self-contained CLI script. ESM format with node shebang.
- **Node.js test runner over Jest/Vitest**: Zero extra test dependencies. `tsx` provides TypeScript support. Test files use `node:test` and `node:assert`.
- **`src/node/` directory structure**: All TypeScript source lives under `src/node/` with subdirectories `core/` (CLI entry, types, config, fetcher, leaderboard, help-dump, skill, completions), `tui/` (formatter, compositor, panel, watch, rain, colors), and `sync/` (multi-machine sync). This namespaces the shipped Node implementation beside the `src/go/` successor tree (see the Go Transition decision below). Tests are co-located in `__tests__/` folders within each subdirectory.
- **Go Transition: two implementation trees in `main`**
  - **Decision**: `src/node/` is the shipped implementation and `src/go/` is the successor, landing change by change but unshipped (not in the formula, not the installed `tu` binary) until the cutover change flips the formula. Constitution v1.2.0 carries a transitional `## Go Transition` article stating this: Principles I, II, V bind both trees; Principles III, IV, the TypeScript Conventions, and the Test Runner / Test Location constraints bind `src/node/` only; Go tests are `_test.go` siblings of the code they test with no `__tests__/` under `src/go/`; Output Stability and Toolkit Standards bind both trees. `fab/project/config.yaml` lists `source_paths: [src/node/, src/go/]` and adds `**/*_test.go` to `test_paths`. The article is removed at cutover (v2.0.0), when III, IV, and the test sections are rewritten for Go. Plan: `fab/plans/sahil/26-09-15-go-port.md` (D2, D3).
  - **Why**: Without the article every Go file is a Principle III violation ("MUST compile to a single ESM bundle") that the review sub-agent flags on each Phase 1–3 change. One peer-level article that scopes the existing clauses keeps the diff to III/IV at zero and gives the cutover change a single section to delete.
  - **Rejected**: Editing each principle inline with "(applies to `src/node/`)" parentheticals — five scattered edits to unwind later. Appending `src/go/` under the old `source_paths: [src/]` entry — a no-op, since `src/` already covered it as a prefix.
  - *Introduced by*: 260915-n18z-constitution-go-transition
- **`package.json` is the version anchor for both binaries during the transition**
  - **Decision**: `just go-build` stamps the Go binary from `package.json`'s version (`-X main.version=v<version>`), not from `git describe`.
  - **Why**: The TS binary prints `v` + the package.json version and the differential harness byte-diffs `--version`; `release.sh`/`release.yml` also derive the `v*` tag from package.json, so it is the single anchor until `src/node/` is deleted (plan row Z1 switches the stamp to `git describe`).
  - **Rejected**: `git describe --tags --always` as the sibling Go tools do — yields `v0.11.5-3-gabc123` on non-tag commits and would break harness parity.
  - *Introduced by*: 260915-h1iv-go-scaffold
- **Go build output goes to `bin/`, not `dist/`**
  - **Decision**: `just go-build` writes `bin/tu`; `bin/` is gitignored.
  - **Why**: `dist/` is the shipped Node artifact and is listed in `package.json` `files`, so a Go binary there would be swept into the npm pack and blur the "Go is unshipped" line.
  - **Rejected**: `dist/tu-go` — same packaging hazard; `dist/bin/` as fab-kit does — fab-kit has no competing shipped artifact in `dist/`.
  - *Introduced by*: 260915-h1iv-go-scaffold
- **Zero-dependency Go scaffold; CI runs the `just go-*` recipes**
  - **Decision**: The Go module carries no cobra or other dependency yet; the `go-build-and-test` CI job invokes `just go-lint`/`go-build`/`go-test` rather than inlining `go` commands, and `setup-go` runs with `cache: false`.
  - **Why**: Whether the positional grammar is parsed by cobra or by hand is the `command`-package decision (plan rows V2/B8); one definition of "lint" (code-quality: minimum pathways); `setup-go`'s cache requires a `go.sum` that does not exist yet.
  - **Rejected**: Pulling cobra now — a dependency with no consumer; inlining gofmt/vet in YAML as the siblings do — duplicates the justfile definition.
  - *Introduced by*: 260915-h1iv-go-scaffold
- **Homebrew distribution**: Public tap at `sahil87/homebrew-tap` handles versioning and installation.
- **Vendored ccusage binary (single native binary, v20+)**: ccusage is vendored into `dist/vendor/` at build time rather than resolved from `node_modules/.bin/` at runtime. This satisfies Constitution Principle III (no `node_modules` at install time) and simplifies Homebrew distribution. The vendored artifact is a **single native Rust binary** at `dist/vendor/ccusage/bin/ccusage`, exec'd directly (no `node` interpreter). *Why:* `ccusage@20` ships no JS impl — the npm package is a launcher over a per-platform native binary, so copying JS bundles out of the package is impossible. *How platform is selected:* the binary comes from an `@ccusage/ccusage-{platform}-{arch}` optionalDependency; npm installs the host's package at `npm install` time, and because the Homebrew formula builds from source on the user's machine, the correct binary is vendored per-install automatically (no prebuilt bottles, `release.yml`/`Formula/tu.rb` untouched). *Rejected:* the v19.0.3 JS stopgap (lands on an equally dead line, forces a second migration). Dev-mode fallback ensures the `tsx`-based development workflow is unaffected (260320-eu2i, 260703-bxuh).
- **`help-dump` must be an in-binary subcommand, not just a repo script**: shll.ai's pull cron runs `<binary> help-dump` against the **brew-installed** binary, uniform across all 7 tools. tu originally shipped `help-dump` only as a repo build-script (`npm run help-dump`) that needs a source checkout + a locally-built `dist/` — the bottle has no such command, so `tu help-dump` returned `Unknown argument: help-dump` (exit 1) and the puller fell back to last-good every run. This went unnoticed until the pull inversion (260603-dmhw) because tu previously *pushed* the artifact itself, so the puller path was never exercised against tu. Fix: move the frozen-contract assembly into `src/node/core/help-dump.ts` (`buildHelpDoc`, bundled into the binary) and wire `tu help-dump` (`runHelpDump()`); the `.mjs` becomes a thin local wrapper that shells out to the binary. *Lesson:* when a sibling repo's contract says "run `<binary> <cmd>`", the binary must actually implement `<cmd>` — a same-named `npm run` script is not the same surface (260604).
- **Bespoke Node help-dump contract (not the shared Go/Cobra producer)**: tu is a flag-based Node/TS CLI with no walkable subcommand tree, so it cannot reuse the 6 other tools' Go producer that recurses a Cobra tree; it emits a structurally-valid flat contract document (`commands: []`) instead. The pure `buildHelpDoc()` lives in `help-dump.ts` and is unit-tested directly (co-located TS test); it is bundled into the binary, so no runtime `tsx` is needed (Constitution III) (260602-v76l, 260604).
- **Release-merge drives the pipeline via `needs`/outputs, not a tag re-trigger**: a tag pushed with the default `GITHUB_TOKEN` does NOT re-trigger workflows (GitHub's documented loop-prevention), so the release-merge path runs the `release` job in the same run via `needs: tag-on-release-merge` + an `always()`-gated `if` (tolerating the upstream job being skipped on the tag-push/dispatch paths), rather than relying on the suppressed tag push to start a second run. Releases remain tag-anchored. (260602-v76l)
- **shll.ai pull model**: tu writes nothing to `sahil87/shll.ai` — shll.ai pulls on its own daily cron (`scheduled-help-refresh.yml`, direct-commit with `GITHUB_TOKEN`), so a single trusted cron is the only writer of `help/tu.json`. *Rejected:* tu-side push via a PR + `gh pr merge --auto --squash` (never a direct push), which serialized the 7-tool concurrent writes through GitHub to avoid a multi-repo push race — moot with a single cron writer (260603-dmhw, 260602-v76l).
- **Toolkit-standards conformance posture**: tu is a member of the shll toolkit and its constitution (v1.2.0, `### Toolkit Standards` article, Last Amended 2026-09-15) binds any change to the CLI surface, help output, `README.md`, or `docs/site/` to first be checked against the toolkit's published standards — enumerated at runtime via `shll standards`, read via `shll standards <name>` (260717-rdo3). The README head blockquote is the `readme-extraction` standard's mandated HexoKit banner — `> Part of [HexoKit](https://hexokit.com) — see all projects there.` (em dash) — the toolkit's product-first brand surface under the HexoKit rebrand (plan: run-kit `fab/plans/sahil/26-09-10-hexokit-rebrand.md`, row C7; banner text per the standard as revised in sahil87/shll#98 and shipped in shll v0.1.31) (260911-v2cu). Elsewhere the toolkit family is named **"shll toolkit"** in prose and code comments (the README Install section, `docs/site/skill.md`, the exit-code comments, the constitution's Toolkit Standards article) and `shll.ai` remains the live endpoint host (`shll.ai/install`, `shll.ai/tu/commands/`) — those flip in the rebrand's Phase 2 sweep, after shll.ai becomes a redirect host — while `sahil87`-owned identifiers (the `sahil87/tap` Homebrew tap, `github.com/sahil87/…` URLs, the `sahil87/shll` canonical-source reference) are addresses and stay as-is (260718-a3z0, sahil87/shll#56). tu's live surfaces (`README.md`, `docs/site/`, `docs/specs/`) carry no run-kit product mentions; the `run-kit context` verb reference in `src/node/core/__tests__/skill.test.ts` is `rk` substrate and is not a brand surface (260911-v2cu). The standards are versioned with the shll release, so a conformance audit pins the version it ran against. Audited standards to date: `principles`, `help-dump`, `readme-extraction`, `skill` (against **shll v0.0.23**, 2026-07-18, 260717-rdo3; the `skill` standard is adopted per 260717-uch0 — see the "Skill bundle embed" section above), `update`, `version`, `shell-init` (against **shll v0.0.23+**, 2026-07-20, 260719-ba5w), and `readme-extraction` rule 1 re-audited against **shll v0.1.31** (sahil87/shll#98, 2026-09-11, 260911-v2cu). The standard's stale "tu exception" prose (describing tu as flag-based with `root.commands: []`) is an upstream shll-repo doc issue, not a tu violation — tu's flat document passes the shape-agnostic invocation contract + checklist and is NOT flattened to match the prose.
- **Homebrew ask-mode suppression via `HOMEBREW_NO_ASK` env var**:
  - **Decision**: Pass `HOMEBREW_NO_ASK: "1"` in the child environment of the interactive `brew upgrade tu` call (`env: { ...process.env, HOMEBREW_NO_ASK: "1" }`), keeping `stdio: "inherit"`.
  - **Why**: Homebrew 6 made ask mode the default for `brew upgrade`; with inherited stdio both stdin and stdout are TTYs, so `ask.rb`'s `Do you want to proceed with the upgrade? [y/n]` prompt fires and blocks the update indefinitely. The env var is the version-proof disable — `brew upgrade` then runs to completion unattended, which is what `tu update` already promises.
  - **Rejected**: Passing `--no-ask`/`--yes`/`-y` to `brew upgrade` — Homebrew < 6 doesn't know the flag and would error, while an unrecognized env var is harmlessly ignored.
  - *Introduced by*: 260812-wdjt-fix-update-brew-ask-prompt

### Toolkit `update` / `version` / `shell-init` conformance (audited 260719-ba5w)

- **`update` standard** — `tu update` is conformant on the in-place-upgrade, `--skip-brew-update`, exit-code, and brew-only/`/Cellar/`-gate clauses. Two MUSTs were fixed:
  - `tu update --help` (and `-h`) MUST advertise the literal `--skip-brew-update` substring in help output. Previously `tu update --help` dispatched to `runUpdate` and ran a **real update** (help was detected only when `--help` was the *first* arg), so `shll update`'s flag-discovery probe both mutated state and never saw the flag. Now the `update` dispatch short-circuits `--help`/`-h` to `console.log(FULL_HELP)` + exit 0 **before** `runUpdate`, scoped to the `update` subcommand only (other surfaces' `--help` behavior is unchanged). See `cli/data-pipeline.md`.
  - **Brew-timeout safety posture**: the interactive `execSync("brew upgrade tu", { stdio: "inherit", env: { ...process.env, HOMEBREW_NO_ASK: "1" } })` call carries **no `timeout` option** — the standard's `MUST NOT impose a short hard timeout on brew upgrade` clause, whose cited incident is the exact prior `timeout: 120_000` (2026-07-19: a stalled GitHub API call inside `brew upgrade` exceeded a 120s kill, corrupting the keg mid-swap → `zsh: permission denied`). The call is interactive and the user can Ctrl-C; Node's default SIGTERM (never SIGKILL) satisfies the graceful-termination clause. The non-interactive piped brew calls keep generous bounds sized for a network transfer: `brew update --quiet` 600_000 (10 min), `brew info --json=v2 tu` 60_000.
  - **Ask-mode suppression posture**: the same `brew upgrade tu` call passes `HOMEBREW_NO_ASK: "1"` in the child environment, suppressing Homebrew 6's default ask mode (`Do you want to proceed with the upgrade? [y/n]` from `ask.rb`, which fires only when both stdin and stdout are TTYs — exactly what the inherited stdio provides) so `tu update` runs to completion unattended; the `process.env` spread preserves PATH and user `HOMEBREW_*` settings. The env var is used over the `--no-ask`/`--yes`/`-y` flag for cross-version safety: Homebrew < 6 errors on the unknown flag but harmlessly ignores the unrecognized env var (260812-wdjt — see Design Decisions).
- **`version` standard** — `tu --version` (and `-V`/`-v`) already conformant: prints exactly `tu version v{X.Y.Z}` as its only line to stdout, exit 0, no network I/O (`PKG_VERSION` embedded at build time). This audit added the missing pinning test (`cli-version.test.ts`).
- **`shell-init` standard** — the success paths (bash/zsh/fish source on stdout, diagnostics on stderr, exit non-zero on unknown shell) were already conformant. One MUST was fixed: `tu shell-init` with **no argument** previously printed usage to **stdout** and exited **0**; the standard requires a missing/unsupported shell arg to exit non-zero (convention 2) with usage on **stderr** and stdout **empty**, since stdout may be eval'd (`eval "$(tu shell-init …)"`). Now the missing-arg branch writes `SHELL_INIT_USAGE` to stderr and exits `EXIT_USAGE` (2). See `cli/data-pipeline.md`.
- No version file is edited in this change; the `tu shell-init` exit-0→2 / stdout→stderr flip is a breaking output change that rides the minor bump the release-PR flow assigns at release time (Output Stability).
