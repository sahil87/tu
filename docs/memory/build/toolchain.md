# Build & Test Toolchain

## Overview

The project uses esbuild for bundling and Node.js built-in test runner (via `tsx`) for testing. Distributed via Homebrew tap from the sahil87 GitHub org.

## Requirements

- Build MUST use esbuild: `esbuild src/node/core/cli.ts --bundle --platform=node --format=esm --outfile=dist/tu.mjs --banner:js='#!/usr/bin/env node'`
- Tests MUST run via `npx tsx --test 'src/node/**/__tests__/*.test.ts'` (Node.js built-in test runner, not Jest/Vitest)
- TypeScript config: `target: ES2022`, `module: NodeNext`, `strict: true`
- Package MUST be distributed as ESM (`"type": "module"`)
- Binary name MUST be `tu` (via `"bin": { "tu": "dist/tu.mjs" }`)
- `prepublishOnly` MUST run `npm run build`
- Published files: `dist/`, `tu.default.conf`
- Node.js engine requirement: `>= 18`
- Dependencies: `@types/node`, `esbuild`, `tsx`, `typescript`, `ccusage` (single package, `^20.0.14`) — all devDependencies; ccusage is build-time only, vendored into `dist/vendor/` during build. codex/opencode functionality is built into `ccusage` as `ccusage codex`/`ccusage opencode` subcommands (260703-bxuh)
- Vendor distribution: `ccusage@20` ships **no JS implementation** — the main package is a launcher over a per-platform native Rust binary. The build step vendors that single binary into `dist/vendor/ccusage/bin/ccusage` (`chmod 0755`, clean-before-copy via `rm -rf dist/vendor`)
- Platform-package mapping (`scripts/build.sh`): the native binary lives in an `@ccusage/ccusage-{platform}-{arch}` npm package declared as an `optionalDependency` of `ccusage`. `build.sh` derives the host package name via `node -p '`@ccusage/ccusage-${process.platform}-${process.arch}`'` and copies its `bin/ccusage`. npm selects the correct host binary at `npm install` time; because the Homebrew formula builds from source on the user's machine (`npm install --include=dev` + `npm run build`), platform selection is automatic per-install — no per-platform release artifacts and no `release.yml` changes. Supported platforms are exactly Homebrew's: darwin/linux × x64/arm64. win32 is out of the vendor path (Homebrew-only distribution); Windows dev mode still works via the npm launcher
- Fail-loud build guard (`scripts/build.sh`): if the host's `@ccusage/ccusage-{platform}-{arch}/bin/ccusage` is absent, the build prints `error: {pkg} not installed — unsupported platform or npm install skipped optional deps` to stderr and exits 1 (no partial `dist/vendor`). Fail-loud is correct here because this is build-time, not a runtime data source — Constitution II (graceful degradation) governs runtime, not the build
- BIN resolution: Vendor-first — resolves `vendor/` relative to `__dirname` (via `import.meta.url`); falls back to `node_modules/.bin/` when vendor dir absent (dev mode)
- Tool invocation: Vendor mode execs the native binary directly at `${BIN}/ccusage/bin/ccusage` (no `node` interpreter); dev mode uses `${BIN}/ccusage` (the npm JS launcher). See `cli/data-pipeline.md` for the single-binary tool registry and per-tool `prefixArgs`

- Distribution: Homebrew tap at `sahil87/tap`

### Help-dump → shll.ai (build-time CLI help artifact)

- **`help-dump` is an in-binary subcommand** — `tu help-dump` (wired in `cli.ts` → `runHelpDump()`) prints tu's CLI help as the cross-tool contract `{tool, version, schema_version: 1, root: Node}` (where `Node = {name, path, short, usage, text (raw byte-for-byte --help), commands: Node[]}`) to **stdout only**, exit 0, **nothing on stderr** (shll.ai treats any stderr on success as contract drift). The envelope MUST NOT carry `captured_at` — the capture timestamp is owned by shll.ai's puller (a tool cannot know its own capture time), per the toolkit `help-dump` standard (`shll standards help-dump`) (260717-rdo3). tu's document is flat (`commands: []`) because tu prints no per-subcommand help pages. The pure contract assembly lives in `src/node/core/help-dump.ts` (`buildHelpDoc`), bundled into the binary by esbuild and unit-tested directly (the pinning test `src/node/core/__tests__/help-dump.test.ts` asserts `captured_at` is ABSENT).
- This is the surface **shll.ai's pull cron actually invokes** against the brew-installed binary (`<binary> help-dump`, uniform with the 6 Go/Cobra tools). It MUST be a real binary subcommand for that reason — see the gotcha below. `name`/`version`/`description` are embedded at **build time** via esbuild `--define` (`__PKG_NAME__`/`__PKG_VERSION__`/`__PKG_DESCRIPTION__` in `build.sh`), because the Homebrew bottle ships only `dist/` (no `package.json` at runtime). In dev (tsx, defines absent) `cli.ts` falls back to walking up to `package.json` once. The raw help `text` is `FULL_HELP + "\n"`, byte-for-byte identical to `tu --help` (`console.log` appends the newline). This is a build/interop artifact, so it does NOT follow Constitution II graceful degradation — it is deterministic and side-effect-free.
- **`scripts/help-dump.mjs` (run via `npm run help-dump`) is a thin local convenience wrapper** — it runs the built binary `node dist/tu.mjs help-dump`, captures stdout, writes `help/tu.json`, and self-validates. It holds **no contract logic** (no drift risk); the binary is the single source of truth. Still plain `node` (`node:` built-ins only, no tsx — Constitution III).
- `help/tu.json` is a **build-local artifact** — gitignored (`help/`), never committed to the tu repo; `sahil87/shll.ai` is the source of truth. tu does not emit or transport it via CI; the dump is invoked outside tu's CI — locally (`npm run help-dump`), and by shll.ai's pull cron (which runs `tu help-dump` against the brew-installed binary).
- shll.ai **pulls** via its own scheduled cron (`scheduled-help-refresh.yml` in `sahil87/shll.ai`) that `brew install`s tu, runs `tu help-dump`, validates, and **direct-commits** to its own `main` using the default `GITHUB_TOKEN`. The cron is the single trusted writer of `help/tu.json`; tu pushes nothing (260603-dmhw). tu does NOT emit `captured_at`; the puller stamps it after capture, as the standard assigns (260717-rdo3).
- A **`.github/workflows/ci.yml`** runs build + tests (`npm ci`, `npm run build`, `npm test`) on **both** `pull_request: branches: [main]` (to gate merges) **and** `push: branches: [main]` (post-merge / release-merge verification) — single `ubuntu-latest` + node 20 lane, action SHAs pinned identically to `release.yml`. It also defines an aggregating **`ci-gate`** job (`needs: [build-and-test]`, `if: always()`, single `ubuntu-latest` lane) that succeeds only when `build-and-test` succeeded; `if: always()` makes the gate resolve to a definitive pass/fail (a skipped required check would otherwise block PRs). `ci-gate` is the single stable **required status check** that gates PR merges to `main`, enforced by a branch **ruleset** on `main` (applied via `scripts/ci-gate-ruleset.sh` — an idempotent, dry-run-default helper; running the live mutation is a documented admin action, NOT performed by the pipeline). It does NOT publish anything (GitHub Release, Homebrew tap) — those external side effects live in `release.yml` (its `release` job runs on a `v*` tag push, on `workflow_dispatch`, and on a `release`-labeled merge to `main`).
- **`release.yml`**: on the `v*` tag-push path it builds and publishes (GitHub Release + Homebrew tap update); it carries **no help-dump/shll.ai steps** (260603-dmhw). No workflow uses `SHLLAI_TOKEN`. It carries the release-PR-merge entry point — a `tag-on-release-merge` job (on push to `main`) detects a `release`-labeled merged PR, creates+pushes the `v*` tag, and exposes outputs so the `release` job runs in the SAME workflow run via `needs`/`always()`.

### Skill bundle embed → `__SKILL_MD__` (build-time, drift-guarded)

- The `tu skill` agent usage bundle (canonical source `docs/site/skill.md`, 95 lines, ≤150 hard cap) is **embedded at build time as an esbuild `--define` string constant** — `SKILL_DEF=$(node -p 'JSON.stringify(require("fs").readFileSync("docs/site/skill.md", "utf8"))')` piped into the esbuild invocation as `--define:__SKILL_MD__="$SKILL_DEF"`, immediately alongside the `__PKG_VERSION__`/`__PKG_NAME__`/`__PKG_DESCRIPTION__` defines. This reuses the exact `__PKG_*__` mechanism (not an esbuild text loader — zero new build machinery); `JSON.stringify` yields a correctly-quoted single-word JS string literal, so no extra shell escaping. Resolution + dev fallback live in `src/node/core/skill.ts` (`SKILL_MD` typeof-guard, mirroring `cli.ts`'s `__PKG_*__` guard) — see `cli/data-pipeline.md`. The shipped bundle performs NO runtime file read for the bundle (Constitution III); dev/tsx reads the canonical file.
- **Byte-identity is by construction, not a committed copy**: the define reads `docs/site/skill.md` directly at bundle time, so there is **no committed embedded copy and no sync script**. This diverges from the shll `go:embed` sync mechanism, which needs a file copied *inside* the Go package; esbuild `--define` reads the canonical file directly, satisfying the standard's byte-identical-and-guarded intent without the copy.
- **Post-build drift guard** (`scripts/build.sh`, after the esbuild + vendor steps so a complete build is validated): `node dist/tu.mjs skill | cmp -s - docs/site/skill.md` — on mismatch prints `error: tu skill output drifted from docs/site/skill.md` to stderr and `exit 1`. This is the layer that guards the **shipped artifact** (the tsx unit tests never exercise `dist/tu.mjs`); it is placed after vendoring to run against the same bundle users ship. Fail-loud is correct here — build-time, not a runtime data source (Constitution II governs runtime, not the build), mirroring the vendor fail-loud guard. A co-located tsx test (`src/node/core/__tests__/skill.test.ts`) additionally pins the dev-fallback path: `SKILL_MD` byte-identity vs. the canonical file, ≤150-line budget, static-only sanity, and the CLI `skill` dispatch contract (stdout=bundle, empty stderr, no non-zero exit).

## Design Decisions

- **esbuild over tsc**: Single-file bundle avoids `node_modules` resolution at runtime and produces a self-contained CLI script. ESM format with node shebang.
- **Node.js test runner over Jest/Vitest**: Zero extra test dependencies. `tsx` provides TypeScript support. Test files use `node:test` and `node:assert`.
- **`src/node/` directory structure**: All TypeScript source lives under `src/node/` with subdirectories `core/` (CLI entry, types, config, fetcher), `tui/` (formatter, compositor, panels, watch, rain, sparkline, colors), `sync/` (multi-machine sync), and `scripts/` (release tooling). This namespaces the Node implementation to allow a future `src/rust/` sibling. Tests are co-located in `__tests__/` folders within each subdirectory.
- **Homebrew distribution**: Public tap at `sahil87/homebrew-tap` handles versioning and installation.
- **Vendored ccusage binary (single native binary, v20+)**: ccusage is vendored into `dist/vendor/` at build time rather than resolved from `node_modules/.bin/` at runtime. This satisfies Constitution Principle III (no `node_modules` at install time) and simplifies Homebrew distribution. The vendored artifact is a **single native Rust binary** at `dist/vendor/ccusage/bin/ccusage`, exec'd directly (no `node` interpreter). *Why:* `ccusage@20` ships no JS impl — the npm package is a launcher over a per-platform native binary, so copying JS bundles out of the package is impossible. *How platform is selected:* the binary comes from an `@ccusage/ccusage-{platform}-{arch}` optionalDependency; npm installs the host's package at `npm install` time, and because the Homebrew formula builds from source on the user's machine, the correct binary is vendored per-install automatically (no prebuilt bottles, `release.yml`/`Formula/tu.rb` untouched). *Rejected:* the v19.0.3 JS stopgap (lands on an equally dead line, forces a second migration). Dev-mode fallback ensures the `tsx`-based development workflow is unaffected (260320-eu2i, 260703-bxuh).
- **`help-dump` must be an in-binary subcommand, not just a repo script**: shll.ai's pull cron runs `<binary> help-dump` against the **brew-installed** binary, uniform across all 7 tools. tu originally shipped `help-dump` only as a repo build-script (`npm run help-dump`) that needs a source checkout + a locally-built `dist/` — the bottle has no such command, so `tu help-dump` returned `Unknown argument: help-dump` (exit 1) and the puller fell back to last-good every run. This went unnoticed until the pull inversion (260603-dmhw) because tu previously *pushed* the artifact itself, so the puller path was never exercised against tu. Fix: move the frozen-contract assembly into `src/node/core/help-dump.ts` (`buildHelpDoc`, bundled into the binary) and wire `tu help-dump` (`runHelpDump()`); the `.mjs` becomes a thin local wrapper that shells out to the binary. *Lesson:* when a sibling repo's contract says "run `<binary> <cmd>`", the binary must actually implement `<cmd>` — a same-named `npm run` script is not the same surface (260604).
- **Bespoke Node help-dump contract (not the shared Go/Cobra producer)**: tu is a flag-based Node/TS CLI with no walkable subcommand tree, so it cannot reuse the 6 other tools' Go producer that recurses a Cobra tree; it emits a structurally-valid flat contract document (`commands: []`) instead. The pure `buildHelpDoc()` lives in `help-dump.ts` and is unit-tested directly (co-located TS test); it is bundled into the binary, so no runtime `tsx` is needed (Constitution III) (260602-v76l, 260604).
- **Release-merge drives the pipeline via `needs`/outputs, not a tag re-trigger**: a tag pushed with the default `GITHUB_TOKEN` does NOT re-trigger workflows (GitHub's documented loop-prevention), so the release-merge path runs the `release` job in the same run via `needs: tag-on-release-merge` + an `always()`-gated `if` (tolerating the upstream job being skipped on the tag-push/dispatch paths), rather than relying on the suppressed tag push to start a second run. Releases remain tag-anchored. (260602-v76l)
- **shll.ai pull model**: tu writes nothing to `sahil87/shll.ai` — shll.ai pulls on its own daily cron (`scheduled-help-refresh.yml`, direct-commit with `GITHUB_TOKEN`), so a single trusted cron is the only writer of `help/tu.json`. *Rejected:* tu-side push via a PR + `gh pr merge --auto --squash` (never a direct push), which serialized the 7-tool concurrent writes through GitHub to avoid a multi-repo push race — moot with a single cron writer (260603-dmhw, 260602-v76l).
- **Toolkit-standards conformance posture**: tu is a member of the shll toolkit and its constitution (v1.1.0, `### Toolkit Standards` article, Last Amended 2026-07-18) binds any change to the CLI surface, help output, `README.md`, or `docs/site/` to first be checked against the toolkit's published standards — enumerated at runtime via `shll standards`, read via `shll standards <name>` (260717-rdo3). The toolkit's standardized name is **"shll toolkit"** — prose and comments across this repo (README head blockquote, `docs/`, code comments, the constitution's Toolkit Standards article) use that name, while `sahil87`-owned identifiers (the `sahil87/tap` Homebrew tap, `github.com/sahil87/…` URLs, the `sahil87/shll` canonical-source reference) are addresses and stay as-is (260718-a3z0, sahil87/shll#56). The standards are versioned with the shll release, so a conformance audit pins the version it ran against; the most recent full audit ran against **shll v0.0.23** (2026-07-18) over the four standards then served — `principles`, `help-dump`, `readme-extraction`, `skill` (260717-rdo3). The `skill` standard is adopted (260717-uch0) — see the "Skill bundle embed" section above. The standard's stale "tu exception" prose (describing tu as flag-based with `root.commands: []`) is an upstream shll-repo doc issue, not a tu violation — tu's flat document passes the shape-agnostic invocation contract + checklist and is NOT flattened to match the prose.
