# tu Go port — rebuild the internals in Go behind unchanged external contracts

> Plan doc — written 2026-09-15 from the sunny-turtle `/fab-discuss` thread.
> Single repo (`sahil87/tu`). This doc owns the decision log, the target
> architecture, the change breakdown, the cutover criteria, and the status of
> each row. Rows become fab changes; update the status column as they land.
> Guiding lights: the toolkit principles (`shll standards principles`) and the
> six sibling Go repos (`shll`, `idea`, `hop`, `wt`, `run-kit`, `fab-kit`).

**Goal**: tu becomes a Go binary distributed like its six siblings (prebuilt
per-platform tarball, generated formula, no runtime dependency), with the
internals redesigned as a pipeline of pure stages rather than translated
line-for-line from TypeScript. Every external surface stays fixed: the CLI
grammar, `--help` text, table/JSON/CSV/Markdown output, exit codes, `tu.conf`
and `org.conf`, the metrics-repo JSONL layout and its never-shrink guard, and
the toolkit contracts (`--version`, `help-dump`, `update`, `shell-init`,
`skill`, config-home).

**Not a goal**: changing what tu does. Behavior changes wait for the port to
ship, then land Go-only.

**Status (2026-09-16)**: Phase 0 in progress. P0 (#78), P1 (#79), P2 (#80), P3a (#81) merged; P4 is the last Phase 0 row, then gate G0 (24 `[DECIDE]` markers in `docs/specs/usage.md` § Drop at cutover). D1–D13 remain proposals until marked confirmed.

---

## Why this shape (the evidence)

- **tu is the odd one out.** Six toolkit tools are Go + cobra + x/term. tu is
  the only Node tool, the only formula with `depends_on "node"`, and the only
  one that builds from source on the user's machine on every install and every
  `tu update` (npm install of esbuild, typescript, tsx, ccusage, then a bundle).
  Its own `help-dump.ts` header calls it "the odd one out"; the toolkit standards
  carry a "tu exception".
- **The heavy path is already native.** `ccusage@20` is a Rust binary vendored
  at build time. Node runs only tu's glue. Measured 2026-09-15 on dev-ws-sahil02:
  `tu --version` 0.03s / 55 MB; `tu` cached 0.27–0.67s; `tu --fresh` 0.86–1.22s;
  ccusage alone for all sources 0.83s / 420 MB; `fab --version` 0.00s / 5 MB.
  Runtime speed is therefore **not** a driver. Install time, dependency
  footprint and toolkit uniformity are.
- **The room was left on purpose.** Change `260306-x861` moved everything under
  `src/node/` "to allow a future sibling" implementation. fab-kit already uses
  `src/go/`.
- **The current architecture is tangled in three specific ways** (read
  2026-09-15, not guessed):
  1. `cli.ts` (2064 lines, 70 functions) hand-codes dispatch combinatorially:
     {snapshot, history, leaderboard} × {by-machine, multi, single} × {print,
     `*Lines` for watch} — 14 near-identical functions, each a copy of the same
     12-line fetch/find/render block with one call swapped.
  2. The output channel leaks into every layer: `formatter.ts` has print/render
     twins for every table; `cli.ts` has 107 direct console/exit sites; results
     for the watch panel travel sideways through module globals
     (`_lastRenderCost`, `_lastRenderCostMap`, `_lastRenderTotalTokens`).
  3. There is no dataset, only ad-hoc pivots: tool, user and machine are
     dimensions but live as map keys, tuple shapes and separate fetch functions;
     by-tool, by-machine and by-user are three code paths doing one group-by.
     `sync.ts` reaches into `fetcher.ts` for the tool registry.
- **The specs are already language-neutral.** `docs/specs/usage.md` and
  `docs/specs/layouts.md` describe the surfaces without reference to Node. They
  are the port's contract. The memory files describe what the TS actually does
  and are the reconciliation source.

## Decisions

| # | Decision | Status | Rationale |
|---|----------|--------|-----------|
| D1 | **Full port, not a module split.** Go owns the whole CLI surface at cutover. No Go-core/TS-TUI hybrid, no Go shim exec'ing node. | proposed | Two runtimes for a 6k-line tool means double packaging and IPC. The only sane split is temporal (this plan's phases). |
| D2 | **Both codebases in `main`, Go unshipped until cutover.** `src/node/` stays the shipped artifact; `src/go/` lands dark, change by change, gated by CI. No long-lived integration branch. | proposed | Long-lived branches rot against a moving `main`. The formula decides what ships, not the branch. |
| D3 | **Constitution amended first (Phase 0), not last.** Add a transitional article: `src/go/` is the successor implementation, unshipped until cutover; Go tests are `_test.go` siblings (Go idiom), the `__tests__/` clause applies to `src/node/` only. `config.yaml` gains `src/go/` in `source_paths` and `**/*_test.go` in `test_paths`. Principles I, II, V unchanged. III, IV and the test sections get their Go rewrite at cutover (v2.0.0). | proposed | Without it every Go change violates Principle III ("MUST compile to a single ESM bundle") and the fab reviewer flags it each time. |
| D4 | **Feature freeze on `src/node/` for the duration.** Bug fixes only; every fix adds a harness fixture and is ported in the same window. New features wait for cutover and land Go-only. | proposed | Every TS feature landed mid-port is written twice. The open backlog rows (`gmcp` etc.) become Go-only rows after Phase 4. |
| D5 | **Layout mirrors the siblings, shifted one level.** `src/go/go.mod` (module `github.com/sahil87/tu`, go 1.25), `src/go/cmd/tu/`, `src/go/internal/<pkg>/`. Toolkit-standard files (`help_dump.go`, `update.go`, `shell_init.go`, `skill.go`, version via `-ldflags`) copied from `idea`/`hop`, which copy rather than share. | proposed | Same shape as `idea`, `hop`, `wt` (`src/cmd`, `src/internal`); `src/go/` because `src/node/` already exists (fab-kit precedent). |
| D6 | **Differential harness is a first-class deliverable and the release gate.** A Go program (`src/go/cmd/tudiff`) plus a language-neutral fixture corpus (`harness/`): a fake `ccusage` on PATH replaying JSON per (subcommand, period, args), a fake `git`, a temp `$HOME` with conf variants, an argument matrix; byte-diff of stdout, stderr and exit code between `node dist/tu.mjs` and the Go binary. | proposed | Replaces most of the 11.5k lines of string-assertion tests for *verifying the port*, and lets the internals change freely. Byte-identical output is the bar; the Output Stability clause makes any drift a release decision, not an accident. |
| D7 | **Fixture capture is real work, not an afterthought.** Add a capture mode (record real ccusage JSON per source, redact project paths) and verify the shapes for all six sources against machines that actually have codex/opencode/gemini/copilot/kimi data. **Real captures are never committed** — they carry the capturing user's spend and the repo is public; they stay under a gitignored `harness/fixtures/<machine>/` and the committed corpus is the schema-derived `_placeholder/` set. dev-ws-sahil02 has real claude, codex, gemini, kimi data; opencode and copilot are empty there (2026-09-16). | proposed | Shapes for gemini/copilot/kimi are recorded in the backlog as "unconfirmed". The harness is only as good as its corpus; the harness runs against local captures where they exist and placeholders otherwise. |
| D8 | **Dogfood via release assets, not a second formula.** From Phase 3 the release job also builds and uploads `tu-go-<os>-<arch>.tar.gz` assets while the formula still ships `tu.mjs`. Maintainer machines install the Go binary manually for the dogfood window. Cutover flips the formula. | proposed | A temporary `tu-go` formula would touch the roster, `shll install`, and the install-composition standard for a throwaway. Assets are invisible to users. |
| D9 | **Cutover is a minor bump, 0.12.0.** Not 1.0.0. | proposed | Output Stability requires a minor bump for a distribution change even when output is byte-identical. 1.0 is a product statement; make it separately if wanted. |
| D10 | **`src/node/` is deleted two releases after cutover**, not at cutover. The differential harness keeps running against the last TS release artifact until then. | proposed | Rollback path: `Formula/tu.rb` can be pointed back at the TS build in one commit while the code still exists. |
| D11 | **Metrics-repo format and never-shrink guard are ported faithfully first, redesigned never in this plan.** Covered by the harness (dry-run and live against a temp bare repo) before any surrounding code is touched. | proposed | It is a wire protocol between machines on different versions. The backlog records a data-loss incident (`0bb81ca`, 2026-05-30) from getting this wrong once. |
| D12 | **Watch mode is hand-rolled on `x/term`, no TUI framework.** Goroutines, `time.Ticker`, `SIGWINCH`, raw-mode key reader, compositor kept as a concept. | proposed | Siblings avoid frameworks; the constitution prizes fast startup; bubbletea is a large dependency for one mode. |
| D13 | **Deployment is a single formula flip, not a side-by-side install for users.** The only "both at once" window is R2 (maintainer machines, via release assets). No `tu-go` binary in the formula, no `TU_IMPL=node` escape hatch, no second formula. Rollback is one commit reverting `Formula/tu.rb` to the TS build (kept buildable until Z1). | proposed | See "Deployment" below. |

## Target architecture (`src/go/internal/`)

A pipeline of pure stages. I/O only at the two ends: `source` (exec, files,
git) and `cmd/tu` + `watch` (stdout, terminal). Everything between returns
values.

| Package | Responsibility | Replaces |
|---------|---------------|----------|
| `fact` | The one fact type: `{Date, Tool, User, Machine, Totals}` and `Totals` (cost + five token counters). ISO labels only (Principle V). | `types.ts` (flat `UsageEntry`), plus the ad-hoc `Map<tool, Totals>`, `{entries, machines}` and leaderboard tuple shapes |
| `source` | Adapters producing `[]fact.Record`: `ccusage` (exec with context timeout, JSON normalize, per-tool `labelKey`), `metrics` (read the metrics repo), `cache` (on-disk JSON keyed by hash of tool+period+args, 60s TTL). Typed per-source errors collected, never thrown through. | `fetcher.ts` exec/parse/cache; the `fetchToolMerged*` family in `cli.ts` |
| `query` | Pure: window filter (`since`/`until`), user/tool filter, daily→weekly/monthly roll-up, `GroupBy(dims...)` — **one** group-by for tool, machine and user pivots. | `aggregateForPeriod`, `aggregateMonthly/Weekly`, `buildSnapshotMachineCosts`, `buildHistoryMachineCosts`, `readAllUsersByUser*`, `foldLeaderboardColumns` |
| `view` | Pure: query result → table model (columns, rows, cells, deltas, bar scales, legend). No ANSI. | the model-shaping halves of `renderTotal`, `renderHistory`, `renderTotalHistory`, `renderLeaderboard` |
| `render` | Encoders from table model to `[]string` / `io.Writer`: `ansi` (tables, bars, sparklines, stacked bars, colors, `NO_COLOR`), `json`, `csv`, `markdown`. **Nothing prints.** | `formatter.ts` (print/render twins collapse), `colors.ts`, `sparkline.ts`, `emitJson/Csv/Markdown` |
| `command` | Parse the positional grammar into `Request{Source, Period, Display, Format, Flags}`; compose source→query→view→render; return `Result{Lines, TotalCost, CostByItem, TotalTokens}`. | `parseDataArgs`, `parseGlobalFlags`, the 14 `dispatch*`/`dispatch*Lines` functions, the `_lastRender*` globals |
| `sync` | Metrics-repo writer (never-shrink guard, day-file layout, commit message), git driver, dry-run report sharing the live decision path. Depends on `fact` + `source/metrics`, not on the ccusage adapter. | `sync.ts` |
| `config` | `tu.conf` / `org.conf` / legacy cascade, config-home standard, `init-conf`, `status` data. | `config.ts`, `runInitConf`, `runStatus` |
| `watch` | Ticker loop calling `command.Run` for lines + stats; compositor; rain layer; panel; raw stdin; resize. | `watch.ts`, `compositor.ts`, `rain.ts`, `panel.ts`, and the `*Lines` dispatch twins |
| `toolkit` | `--version` (ldflags), `help-dump` (flat contract, byte-identical `--help`), `update`, `shell-init`, `skill` (`go:embed` of `docs/site/skill.md` + drift guard), completions. | `help-dump.ts`, `skill.ts`, `completions.ts`, `runUpdate`, `runShellInit` |

Go-native choices taken along the way: `errgroup` for parallel per-tool
fetches with a per-source deadline; JSON output defined as Go structs (the
schema becomes code); golden-file tests for `render` with an `-update` flag;
table-driven tests for `query` and `command` parsing; `go-runewidth` only if a
glyph audit finds a non-single-width character (the current set is all
single-width BMP).

## Execution by the operator

The rows are written to be handed to `/fab-operator` as queues in `merge-auto`
mode. How that mode behaves, verified against the operator skill 2026-09-15:

- **Strictly serial.** The operator arms each PR with auto-merge on completion
  and defers the next spawn to the tick that verifies the merge, then rebases
  the next change onto the advanced `main`. One row in flight at a time. This
  is the right shape for this plan: Phase 1 and 2 rows all touch
  `src/go/internal/`, and concurrent rows would conflict on rebase.
- **`depends_on` is a misfit in `merge-auto`.** Implicit chaining is disabled
  and same-repo `depends_on` entries trigger the operator's mode question. The
  **Depends** column is therefore documentation; the **row order within each
  phase is the execution order** and already respects every dependency. Hand
  the operator the rows in order with no dependency annotations.
- **Rebase conflict mid-queue is a silent skip in `merge-auto`.** The operator
  `track rm`s the row and moves on. With serial execution this should be rare,
  but a skipped row starves everything after it. **Standing instruction to the
  operator: escalate on rebase conflict instead of skipping.** At each gate,
  check the operator's skipped list before proceeding.
- **Row → change.** Each row's Scope column is the raw text for `/fab-new`.
  Prefix every row with the same context line so the intake agent reads this
  doc first:
  `Context: fab/plans/sahil/26-09-15-go-port.md, row <ID>. Read the Decisions and Target architecture sections before writing the intake. Do not change any external surface listed under Goal.`
  The `fab-fff` intake gate (flat 3.0) is the automatic filter: a row whose
  intake scores below it stops and is reported, which is the signal that the
  row needs more detail here, not a reason to `--force`.
- **Rows the operator cannot run** are marked *(human)* or *(human gate)*:
  P3b, V3/G1, R2, and the two-release wait before Z1. X4 is cross-repo and runs
  as an ordering-only barrier.

### Releases and installing a build

Releases are manual and tag-anchored. Nothing in this plan cuts one
automatically; the operator never runs `just release`.

- **Cut a release**: from a checkout at the latest `origin/main`,
  `just release` (patch) or `just release minor` (X1). `scripts/release.sh`
  bumps `package.json`, commits, tags `v*`, pushes; `release.yml` does the
  rest — GitHub Release, and from R1 onward the `tu-go-*` assets too. The
  release-labeled-PR path exists as an alternative entry point.
- **Get the released build on a machine**: `tu update` — but only for what the
  **formula** ships. Before X1 that is the Node build; from X1 it is the Go
  binary. The dogfood build in R2 is an asset, not a formula, so it is
  installed and refreshed with `just dogfood-install` (R1) and never through
  `tu update`.
- **Who cuts what**: R2 needs one release for assets to exist, X1 is the
  0.12.0 release, Z1 waits for two more. All three are Sahil's `just release`
  runs, so G2, G3 and Z1 are human stops for that reason as much as for the
  review.

### G1 review protocol (agent gate)

G1 is a review loop the operator runs without Sahil. It starts on the tick that
verifies B2's merge.

**Reviewer.** The operator sends the review request as a cross-session message
to the `sunny-turtle` session (the session that wrote this plan; visible in
`ListAgents`). If that session is not listed, the operator spawns a bare agent
in a fresh `tu` worktree on `origin/main` and gives it the same request. Either
way the reviewer is an agent with this plan open, not a person.

**Request.** The message carries: the plan path and the instruction to read
§ Decisions, § Target architecture and `fab/project/code-quality.md` first; the
list of merged PRs for V1, V2, B1, B2; the latest harness report location; and
the verdict file path `fab/plans/sahil/reviews/g1-<n>.md` where `n` is the
cycle number starting at 1.

**Checklist.** The reviewer answers each item with a finding or "ok":

1. Package boundaries match § Target architecture: `source` is the only
   package that execs or reads files; `query`, `view`, `render` import no I/O;
   `command` composes and returns a `Result`, nothing prints below `cmd/tu`.
2. One group-by: tool, machine and user pivots share `query.GroupBy`; no
   per-dimension aggregation code.
3. No result globals; the watch-facing stats travel in `command.Result`.
4. Errors are typed per source and surfaced at the edge; no `os.Exit` or
   stderr writes below `cmd/tu`.
5. Tests: `query` and `command` parsing are table-driven; `render` uses golden
   files with an update flag; no string-assertion sprawl copied from the TS
   tests.
6. Harness: the diff count fell for every case class the four rows claim
   (single-mode snapshot, history, all four formats, conf variants); every
   remaining red case is explained by a not-yet-ported row, not by a defect.
7. Constitution: Principles I, II, V hold; the Go Transition article's
   "unshipped" clause holds (formula, `bin/tu` not on any PATH the release
   touches).
8. `gofmt`, `go vet`, `just go-test` clean on `origin/main`.

**Verdict file.** `fab/plans/sahil/reviews/g1-<n>.md` with a first line of
exactly `Verdict: GO` or `Verdict: REWORK`, then numbered findings, each with
file references and the checklist item it fails. A `GO` may still carry
findings marked *follow-up*; those become backlog rows, not rework. The
reviewer commits the file to `main` directly (plan-doc precedent) and replies
to the operator with the verdict line and the file path.

**Loop.** On `GO`: the reviewer updates the V3 row status in this doc (the
operator never edits files) and the operator continues with B8. On `REWORK`: the operator spawns one fab change `g1-rework-<n>` via
`fab-new` whose raw text is the verdict file's findings verbatim plus the
standard context prefix, waits for its verified merge, then re-runs the review
as cycle `n+1`. After **three** consecutive `REWORK` verdicts the operator
stops and escalates to Sahil with the three verdict files. The reviewer MUST
NOT widen scope: findings are limited to the checklist; anything else is a
*follow-up*.

## Deployment (D13)

Three shapes were considered for how users receive the Go binary.

| Shape | What users see | Cost | Verdict |
|-------|----------------|------|---------|
| **A. Formula flip** (chosen) | `tu update` at 0.12.0 installs the Go tarball. Nothing else changes: same binary name, same conf, same metrics repo. | Rollback is a tap commit pointing `tu.rb` back at the TS build; users run `tu update` again. A field divergence is visible for as long as it takes to notice and revert. | **Chosen.** The harness gives byte-identical evidence before the flip, R2 dogfoods on three real machines, the user base is small, and the constitution names `tu` as the one binary. |
| B. Side-by-side `tu` + `tu-go` in one formula | Two binaries for a few releases; users opt in to `tu-go`. | Formula keeps `depends_on "node"` (the main thing being removed); two binaries share cache and metrics repo; `shll version`/`doctor` and `tu update` know nothing about `tu-go`; the name churns away later; adoption depends on users noticing. | Rejected. Doubles the surface for one release and delays the benefit. |
| C. Go `tu` with a `TU_IMPL=node` escape hatch execing the bundled `tu.mjs` | One binary name; a user who hits a divergence flips back per-machine and reports it. | Formula keeps node for one more release; a shim path in the Go binary that exists only to be deleted; the escape hatch itself is untested surface. | Rejected for the same reason as B, but it is the fallback if R2 surfaces divergences that cannot be closed before a release deadline. |

Two things are true regardless of shape and are what the plan actually
guards:

- **A mixed fleet is unavoidable.** Users upgrade at different times, so TS
  0.11.x and Go 0.12.x will co-write the metrics repo for weeks. That, not the
  install, is the real "both deployed together" period. Criterion 2 below and
  D11 exist for it.
- **The worst field failure is a bad sync write, not a wrong table.** Wrong
  output is annoying and reverts cleanly. A bad write is bounded by the
  never-shrink guard and recoverable from git history (the 2026-06 repair
  script is the precedent), which is why B6 is ported faithfully and gated on
  live-sync parity before anything ships.

## Cutover criteria (all must hold before X1)

1. `tudiff` full matrix: zero unexpected diffs across single/multi/org/legacy
   conf variants, all six sources, all periods, all display types, all four
   output formats, `NO_COLOR` and TTY/pipe, on linux-amd64 and darwin-arm64.
2. Live sync parity: a Go sync and a TS sync from the same local state against
   a temp clone of the real metrics repo produce identical day-files and an
   identical `git status --porcelain`.
3. Dogfood: one day on the three maintainer machines with R2's event checklist complete (midnight rollover, foreign-commit sync, watch session, every display type and format) and no divergence rows open.
4. Toolkit audit: `shll doctor` and `shll version` green against the Go binary;
   each of `version`, `help-dump`, `update`, `shell-init`, `skill`,
   `config-home`, `install-composition` re-audited and the shll version recorded
   in `docs/memory/build/`.
5. `brew install` from the generated formula on a clean macOS and a clean Linux
   box completes without `node` present.

## Risks

- **Output parity on the formatter** is the largest single risk (1842 lines of
  byte-exact tables). Mitigation: harness first (P4), snapshot first (V2), and
  `render` isolated behind a table model so padding/ANSI logic lives in one
  place.
- **Fixture coverage for non-Claude sources.** Mitigation: P3 is its own row
  with an explicit ask to other users; shapes recorded as unconfirmed stay
  flagged in the harness until a real capture exists.
- **Date semantics.** 31 `new Date(...)` sites in TS; local vs UTC intent must
  be checked per site during V1/B2. Harness runs under a fixed `TZ` and a
  second `TZ` to catch it.
- **Cross-version sync.** Old TS binaries keep writing to the metrics repo
  after cutover. D11 + criterion 2 cover it; Z1 waits two releases.
- **Scope creep under the banner of "rethink".** D4 freeze plus P1's explicit
  drop list are the guard. Anything not in the drop list is a behavior to keep.

## Out of scope for this plan

- New features (gemini/copilot column fit, weekly label changes, etc.) — after Z2.
- Windows distribution, even though ccusage ships win32 binaries — Homebrew-only stays.
- Renaming, 1.0, or anything under the HexoKit rebrand — tracked in run-kit's plan.
- A shared Go library for the toolkit standards layer — siblings copy; tu copies too.
