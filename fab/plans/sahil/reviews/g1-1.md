## Rework findings

1. **`command` is welded to the ccusage adapter; the `Fetcher` interface is nominal.**
   (checklist item 1)
   `internal/command/run.go:20-24` declares `Fetcher.Fetch(ctx, tool ccusage.Tool, …)`,
   and `run.go:77-112,158-161` read `ccusage.Tools`, `ccusage.Lookup`,
   `ccusage.PeriodDaily`, `ccusage.DefaultTimeout`. The tool registry (key,
   display name, column order) is a property of the fact model, not of one
   adapter; B3's `source/metrics` must implement `Fetcher` and cannot without
   importing the ccusage package for its parameter type, and `command` will
   otherwise grow a second concrete import. Fix: move `Tool{Key, Name}`,
   `Tools` (column order) and `Lookup` to `internal/fact` (or a tiny
   `internal/tools`); keep `PrefixArgs`/`LabelKey` in `ccusage` as an
   adapter-private map keyed by `fact` key; `Fetcher.Fetch` takes the
   `fact.Tool` (or the key string); move `PeriodDaily`/`DefaultTimeout` to
   `source` or `command`. After the fix `command` imports `source` and `fact`
   for fetching and no `source/*` adapter; `cmd/tu` is the only place that
   names `ccusage`.

2. **`view.TotalHistory` is a 132-line function that B4 and B5 are about to extend.**
   (checklist item 1; `fab/project/code-quality.md` "God functions (>50 lines)")
   `internal/view/pivot.go:46-178`. Its own doc comment already reserves "the
   lbh hooks are B5", and B4 adds machine columns to the same table. It
   currently interleaves five concerns: label union and value map, the
   significance filter, the width budget, bar scale/apportioning, and row
   assembly. Fix: extract at least `pivotWidths(...)`, `pivotRows(...)` and
   the value-map build into named helpers so B4/B5 add a column source and a
   row source rather than more lines in one body. `History` (83 lines,
   `history.go`) shares the same structure and should follow the same split
   so the two tables stay parallel. `command/parse.go` `Parse` (89) /
   `scanFlags` (85) are long but flat flag tables; leave them.

## Follow-ups (not rework; open as backlog rows)

3. **`view` imports `render` for `FormatInt`/`FormatCost`** (22 call sites in
   `view/*.go`). The model layer depends on the encoder root for number
   formatting, inverting the plan's direction. Move the two formatters to
   `view` (cells are pre-formatted text, so `view` is where they belong) or
   to a leaf `internal/format` both can import. Cosmetic today; do it when a
   row next touches both packages.

4. **Test volume is trending toward the TS sprawl.** 9,494 lines of `_test.go`
   for four rows against 11,508 lines of TS tests for the whole tool. The
   shape is right (41 golden files under `render/*/testdata`, table-driven
   `query`/`command` tests), but each row is also re-asserting behavior the
   harness now pins byte-for-byte. From B3 on, prefer one harness case over a
   Go test for any behavior visible at the CLI surface, and keep Go tests for
   the pure packages.

5. **`render/json` and `render/csv` encode from `view.ToolTotals`/`view.Series`
   while `render/ansi`/`markdown` encode from `view.Table`.** Deliberate
   (JSON needs raw numbers) and fine; note it in
   `docs/memory/go-port/query-view-render.md` so B5's leaderboard JSON
   follows the same split instead of inventing a third shape.
